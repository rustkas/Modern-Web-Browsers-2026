# Глава 2. Потоки, параллелизм и шедулинг

В архитектуре браузера 2026 года управление потоками выполнения вышло далеко за рамки простой обработки скриптов. Поскольку современный браузер функционирует как мета-операционная система, эффективное распределение вычислительных ресурсов между интерфейсом, сетевыми запросами и тяжелыми вычислениями стало залогом выживания веб-приложения. Центральным элементом этой системы остается механизм координации задач, который эволюционировал для обеспечения экстремальной отзывчивости.

Эта глава детально разбирает Event Loop 2026 года, механизмы параллелизма (Web Workers и Shared Workers) и относительно новый Prioritized Task Scheduling API. Понимание этих механизмов критически важно для достижения целевых значений Core Web Vitals, особенно INP (Interaction to Next Paint). Отдельно стоит сразу оговориться: часть API, разобранных в этой главе (особенно Scheduler API), пока не является кросс-браузерным стандартом — об этом подробно ниже, в соответствующих разделах.

## 1. Event Loop 2026: Microtasks, MacroTasks и эволюция приоритетов

Несмотря на многопроцессорную архитектуру, выполнение JavaScript в рамках одного **Renderer Process** по-прежнему опирается на **Event Loop**. Основной принцип остался неизменным: цикл событий обрабатывает задачи из очередей, когда основной стек вызовов пуст.

Однако в 2026 году понимание структуры очередей стало критическим для прохождения теста на **INP (Interaction to Next Paint)** — ключевую метрику отзывчивости, порог которой составляет жесткие **200 миллисекунд**.

### 1.1. Структура очередей Event Loop

Современный Event Loop управляет несколькими очередями задач, каждая из которых имеет свой приоритет и правила обработки. В спецификации WHATWG выделяются следующие типы очередей:

- **Task Queue (Очередь макрозадач).** Содержит макрозадачи, поступающие из внешних источников:
    - События таймеров (`setTimeout`, `setInterval`).
    - Сетевые события (завершение загрузки ресурсов, ответы на запросы).
    - События пользовательского интерфейса (клики, движения мыши, нажатия клавиш).
    - Обработчики `postMessage` между вкладками и воркерами.
    - События индексации (`IndexedDB`).
    
    **Важное правило:** за один проход Event Loop выполняется **ровно одна макрозадача** из очереди. После выполнения макрозадачи цикл переходит к обработке всех накопившихся микрозадач, затем выполняет рендеринг (при необходимости) и только потом берет следующую макрозадачу.

- **Microtask Queue (Очередь микрозадач).** Содержит задачи, которые должны быть выполнены как можно скорее, до следующего рендеринга:
    - Обработчики `Promise` (`.then()`, `.catch()`, `.finally()`).
    - `MutationObserver` — обратные вызовы, реагирующие на изменения в DOM.
    - `queueMicrotask()` — метод, позволяющий явно добавить задачу в микрозадачную очередь.
    - Внутренние системные задачи браузера (например, очистка сборщика мусора на микроуровне).

    **Важное правило:** все накопившиеся микрозадачи выполняются непрерывно, одна за другой, пока очередь не опустеет. Если разработчик создает бесконечную цепочку промисов, которая непрерывно добавляет новые микрозадачи, браузер зависает, не переходя к рендерингу. Это называется **микрозадачной петлей (microtask loop)** и приводит к провалу INP.

- **Animation Frame Queue (Очередь кадров анимации).** Содержит задачи, поставленные через `requestAnimationFrame()`. Эти задачи выполняются непосредственно перед рендерингом, строго синхронизированно с частотой обновления экрана (обычно 60 Гц, что дает ~16.67 мс на кадр).

- **Idle Queue (Очередь фоновых задач).** Содержит задачи, поставленные через `requestIdleCallback()`. Эти задачи выполняются только в периоды простоя, когда браузер не занят рендерингом и обработкой пользовательского ввода. Здесь важна оговорка о зрелости: `requestIdleCallback()` до сих пор **не имеет статуса Baseline** — Safari не реализует его в стабильной сборке (функциональность скрыта за экспериментальным feature-флагом), поэтому в продакшн-коде для Safari необходим fallback через `setTimeout`.

### 1.2. Порядок выполнения в Event Loop 2026

Полный порядок работы Event Loop в каждом цикле:

1.  **Выполнить одну макрозадачу.** Браузер выбирает самую старую задачу из очереди макрозадач и выполняет ее.
2.  **Выполнить все микрозадачи.** После завершения макрозадачи браузер входит в цикл обработки микрозадач и выполняет их все, пока очередь не опустеет. Если во время выполнения микрозадачи добавляются новые микрозадачи, они также выполняются в текущем цикле.
3.  **Выполнить requestAnimationFrame.** Если есть зарегистрированные колбэки `requestAnimationFrame`, они выполняются после микрозадач и непосредственно перед рендерингом.
4.  **Рендеринг (при необходимости).** Браузер проверяет, нужно ли обновить экран (например, изменилась геометрия страницы, появились новые тайлы). Если да, он выполняет Layout, Paint и Composite.
5.  **Выполнить requestIdleCallback.** Если после рендеринга остается время до следующей отрисовки (бюджет кадра), браузер выполняет фоновые задачи с низким приоритетом (в тех браузерах, где API реализован — см. оговорку выше).
6.  **Вернуться к шагу 1.** Цикл повторяется бесконечно.

### 1.3. Опасности перегрузки микрозадач

Перегрузка очереди микрозадач — одна из самых частых причин низкого INP в 2026 году.

Типичные сценарии, приводящие к микрозадачной петле:

- **Бесконечные цепочки промисов.** Код, который рекурсивно создает новые промисы, никогда не освобождая цикл.
- **Циклические вызовы MutationObserver.** Один MutationObserver изменяет DOM, что вызывает срабатывание другого MutationObserver, который снова изменяет DOM, и так далее.
- **Синхронные вычисления внутри .then().** Разработчик выполняет тяжелые вычисления внутри обработчика промиса, блокируя очередь микрозадач.

Пример проблемного кода:

```javascript
function problematicLoop() {
    Promise.resolve().then(() => {
        // Выполняется синхронный код, который добавляет новую микрозадачу
        problematicLoop();
    });
}
problematicLoop();
// Браузер зависает — INP провален
```

**Решение:** выносить тяжелые вычисления в Web Workers или использовать Scheduler API с приоритетом `background` (там, где он поддерживается — см. раздел 3) либо обычный `setTimeout(fn, 0)` как универсальный fallback.

## 2. Web Workers и Shared Workers: истинный параллелизм

Для поддержания высокого показателя INP в 2026 году тяжелый код больше не должен исполняться в основном потоке (Main Thread). Браузер как ОС предоставляет механизмы для истинного параллелизма — использования нескольких ядер процессора одновременно.

### 2.1. Web Workers: изолированные фоновые потоки

**Web Workers** позволяют запускать скрипты в фоновых потоках, полностью изолированных от основного потока исполнения. Они не имеют доступа к DOM, `window` объекту и большинству браузерных API, но могут выполнять вычисления, работать с IndexedDB, отправлять сетевые запросы и взаимодействовать с основным потоком через `postMessage()`.

**Типы Web Workers:**

- **Dedicated Worker.** Привязан к одному конкретному скрипту на странице. Наиболее распространенный тип.
- **Shared Worker.** Может использоваться несколькими вкладками одного и того же источника (origin). Это позволяет централизовать управление состоянием, кешированием или сетевыми соединениями.
- **Service Worker.** Специализированный тип воркера, работающий как прокси-сервер между браузером и сетью. Рассматривается отдельно в Главе 10.

**Как использовать Web Worker:**

```javascript
// Основной поток
const worker = new Worker('heavy-computation.js');

worker.postMessage({ data: largeArray, operation: 'process' });

worker.onmessage = (event) => {
    console.log('Результат вычислений:', event.data);
};

// heavy-computation.js (файл воркера)
self.onmessage = (event) => {
    const { data, operation } = event.data;
    // Тяжелые вычисления здесь
    const result = performHeavyComputation(data);
    self.postMessage(result);
};
```

**Где применять Web Workers в 2026 году:**

- Обработка больших массивов данных (JSON, CSV, бинарные файлы).
- Криптографические операции (шифрование, хеширование).
- Локальный инференс нейросетевых моделей — на практике в 2026 году это чаще всего WebGPU-ускоренный стек (transformers.js, ONNX Runtime Web с WebGPU execution provider), запущенный внутри воркера. WebNN как нативный API для этой задачи пока остаётся в статусе Origin Trial только в Chrome, без реализации в Firefox и Safari, — рассматривайте его как перспективное, но не готовое к продакшну направление (подробнее — во Введении).
- Компрессия и декомпрессия данных (zlib, gzip).
- Парсинг сложных форматов (PDF, ZIP, аудио).
- Генерация отчетов, экспорт данных в Excel/CSV.

**Ограничения Web Workers:**

- Нет доступа к DOM — нельзя обновлять интерфейс напрямую.
- Нет доступа к `window` и `document`.
- Обмен данными через `postMessage` включает сериализацию/десериализацию (для больших объектов это может занимать время). Для передачи больших бинарных данных используйте `Transferable objects` (`ArrayBuffer`, `MessagePort`), которые перемещаются без копирования.

**Передача данных через Transferable objects:**

```javascript
// Основной поток
const buffer = new ArrayBuffer(1024 * 1024 * 100); // 100 МБ
worker.postMessage({ buffer }, [buffer]); // buffer перемещается в воркер
// В основном потоке buffer больше недоступен (перемещен)
```

### 2.2. Shared Workers: общие ресурсы между вкладками

**Shared Worker** отличается от Dedicated Worker тем, что один экземпляр воркера обслуживает все вкладки, принадлежащие одному origin.

Использование Shared Workers:

```javascript
// Основной поток
const sharedWorker = new SharedWorker('shared-socket.js');
sharedWorker.port.onmessage = (event) => {
    console.log('Данные из общего воркера:', event.data);
};
sharedWorker.port.start();

// shared-socket.js
const connections = [];

self.onconnect = (event) => {
    const port = event.ports[0];
    connections.push(port);
    
    port.onmessage = (event) => {
        // Отправляем сообщение всем подключенным вкладкам
        connections.forEach(p => p.postMessage(event.data));
    };
    
    port.start();
};
```

**Сценарии использования Shared Workers в 2026 году:**

- Управление WebSocket-соединением между вкладками (одно соединение на все вкладки, экономия ресурсов).
- Общий кеш данных (например, кеш ответов API) для ускорения загрузки в разных вкладках.
- Централизованное логирование и сбор метрик.

## 3. Prioritized Task Scheduling API: контроль приоритетов в реальном времени

Главным новшеством в управлении потоками стал **Prioritized Task Scheduling API** (также известный как Scheduler API или `scheduler.postTask()`). Раньше планирование задач было хаотичным: разработчики использовали `setTimeout(fn, 0)`, чтобы «отложить» выполнение и дать браузеру передохнуть. В Chromium-браузерах этот «хак» заменен на полноценный шедулер — но важно понимать реальный статус этой технологии в 2026 году, прежде чем закладывать её в архитектуру продакшн-приложения.

**Статус кросс-браузерной поддержки.** Scheduler API **не имеет статуса Baseline**. По данным MDN, причина именно в том, что API не работает в части широко используемых браузеров. Практическая картина на 2026 год такая:

- **Chrome/Edge (Chromium)** — полная поддержка `postTask()` и `yield()`, API стабилен и активно используется в продакшне (в том числе такими командами, как Airbnb).
- **Firefox** — поддержка появилась заметно позже Chromium; метод `scheduler.yield()` доступен начиная примерно с августа 2025 года.
- **Safari** — **не реализует ни `postTask()`, ни `yield()`**.

Практический вывод: Scheduler API стоит применять как прогрессивное улучшение (progressive enhancement) с обязательной проверкой доступности и fallback на `setTimeout(fn, 0)`, а не как единственный механизм планирования задач:

```javascript
function scheduleTask(fn, priority = 'user-visible') {
    if ('scheduler' in window && 'postTask' in scheduler) {
        return scheduler.postTask(fn, { priority });
    }
    // Fallback для браузеров без Scheduler API (в первую очередь Safari)
    return new Promise((resolve) => {
        setTimeout(() => resolve(fn()), 0);
    });
}
```

### 3.1. Как работает Scheduler API

Там, где Scheduler API поддерживается, он позволяет явно указывать приоритет каждой задачи, а браузер интеллектуально управляет их выполнением, учитывая загрузку системы, состояние вкладки (активна/в фоне) и текущую нагрузку на GPU.

**Базовый синтаксис:**

```javascript
scheduler.postTask(
    () => {
        // Задача для выполнения
        console.log('Выполняется с приоритетом:', priority);
    },
    {
        priority: 'user-blocking',
        delay: 100, // опционально: задержка в мс
        signal: abortController.signal // опционально: отмена задачи
    }
);
```

### 3.2. Уровни приоритетов

Scheduler API определяет три уровня приоритета:

- **`user-blocking` (высший приоритет).** Задачи, критически важные для взаимодействия с пользователем. Выполняются как можно быстрее, с минимальными задержками.
    - Примеры: обработка клика, обновление состояния ввода текста, анимации, непосредственно влияющие на интерфейс.
    - Если задач с этим приоритетом много, браузер может пожертвовать фоновыми задачами для сохранения отзывчивости.

- **`user-visible` (средний приоритет, значение по умолчанию).** Задачи, которые видит пользователь, но которые не требуют мгновенного ответа.
    - Примеры: рендеринг списка, загрузка изображений, обновление состояния после асинхронного запроса.
    - Браузер стремится выполнить их в течение одного-двух циклов Event Loop, но может отложить, если есть `user-blocking` задачи.

- **`background` (низший приоритет).** Фоновые задачи, невидимые для пользователя.
    - Примеры: сбор аналитики, предварительная загрузка данных, индексация, очистка кеша, автосохранение.
    - Выполняются только тогда, когда система свободна, в периоды бездействия (используют время между кадрами). Если пользователь начинает активно взаимодействовать, браузер приостанавливает эти задачи.

### 3.3. Продвинутое использование Scheduler API

**Динамическое изменение приоритета:**

```javascript
const controller = new TaskController({ priority: 'background' });
const signal = controller.signal;

scheduler.postTask(
    () => { /* задача */ },
    { signal, priority: 'background' }
);

// Позже, если пользователь переключился на вкладку, повышаем приоритет
controller.setPriority('user-visible');
```

**Ожидание смены приоритета:**

```javascript
const signal = scheduler.postTask(
    () => {
        if (signal.priority === 'background') {
            // Задача выполняется в фоне
        }
    },
    { priority: 'background' }
);

signal.onprioritychange = () => {
    console.log('Приоритет изменен:', signal.priority);
};
```

**Отмена задачи:**

```javascript
const abortController = new AbortController();
const signal = abortController.signal;

scheduler.postTask(
    () => { /* задача */ },
    { signal }
);

// Отмена задачи (например, пользователь закрыл вкладку)
abortController.abort();
```

**Использование с `Async`/`Await`:**

```javascript
async function backgroundProcessing() {
    // Выполняем код с низким приоритетом
    await scheduler.postTask(() => {}, { priority: 'background' });
    
    // Тяжелые вычисления здесь
    const result = await heavyComputation();
    
    // Возвращаемся в основной поток с более высоким приоритетом
    await scheduler.postTask(() => {}, { priority: 'user-visible' });
    updateUI(result);
}
```

### 3.4. Прерывание длинных задач: scheduler.yield() и наследие isInputPending()

Помимо расстановки приоритетов, Scheduler API решает вторую задачу — корректное прерывание длинных синхронных вычислений, чтобы браузер успел обработать пользовательский ввод. Современный, рекомендуемый способ это делать — метод **`scheduler.yield()`**, который прерывает выполнение и возвращает управление туда же в очередь, откуда была вызвана задача, сохраняя её относительный приоритет.

Более старый механизм — **`navigator.scheduling.isInputPending()`** — стоит знать, потому что он всё ещё встречается в существующем коде (в первую очередь в кодовой базе Facebook/Meta, откуда API и происходит), но важно понимать его текущий статус: MDN прямо помечает его как **устаревший, вытесненный `scheduler.yield()`** ("superseded"), экспериментальный и практически ограниченный Chromium. Для нового кода в 2026 году предпочтителен `scheduler.yield()` с fallback-проверкой поддержки, а не `isInputPending()`.

Пример на устаревшем API — исторический, для понимания кода в legacy-проектах:

```javascript
// Устаревший подход (Chromium-only, superseded by scheduler.yield())
function processWithYield(data) {
    let index = 0;
    
    while (index < data.length) {
        // Проверяем, есть ли ожидающие события ввода
        if (navigator.scheduling && navigator.scheduling.isInputPending()) {
            // Приостанавливаем выполнение, чтобы не блокировать UI
            setTimeout(() => processWithYield(data.slice(index)), 0);
            return;
        }
        
        // Обрабатываем порцию данных
        processChunk(data, index);
        index += 1000; // по 1000 элементов за раз
    }
}
```

Современный эквивалент через `scheduler.yield()` (там, где API доступен):

```javascript
async function processWithModernYield(data) {
    let index = 0;

    while (index < data.length) {
        processChunk(data, index);
        index += 1000;

        // Отдаём управление браузеру между чанками
        if ('scheduler' in window && 'yield' in scheduler) {
            await scheduler.yield();
        } else {
            await new Promise((resolve) => setTimeout(resolve, 0));
        }
    }
}
```

### 3.5. Интеграция с другими API

Scheduler API интегрируется с другими браузерными API для гибкого управления задачами:

- **`AbortController`** — для отмены задач при уходе пользователя со страницы или при закрытии вкладки.
- **`performance.now()`** — для измерения времени выполнения задач.
- **`TaskSignal`** — для отслеживания изменения приоритета.

### 3.6. Практическое применение в 2026 году

**Пример: редактор документов с автосохранением**

```javascript
// Автосохранение — фоновый приоритет
async function autoSave(document) {
    await scheduleTask(
        () => {
            saveDocumentToStorage(document);
        },
        'background'
    );
}

// Обработка ввода текста — высший приоритет
function onTextInput(event) {
    scheduleTask(
        () => {
            updateDocumentState(event.target.value);
        },
        'user-blocking'
    );
}
```

*(здесь используется обёртка `scheduleTask()` с fallback из раздела 3, чтобы код одинаково работал и в Chromium, и в Firefox, и в Safari)*

**Пример: предзагрузка следующих страниц**

```javascript
// Предзагрузка данных для следующего шага — низкий приоритет
function preloadNextPage(url) {
    scheduleTask(
        () => {
            fetch(url).then(response => response.json()).then(data => {
                // Кешируем данные
            });
        },
        'background'
    );
}
```

## Итог

Современный Event Loop в 2026 году — это сложный механизм координации четырех типов очередей: макрозадачи, микрозадачи, анимационные кадры и фоновые задачи. Понимание порядка их выполнения критически важно для достижения INP ≤ 200 мс. Обратите внимание, что не вся эта инфраструктура одинаково зрела во всех браузерах: `requestIdleCallback()` до сих пор не поддерживается в Safari.

Web Workers обеспечивают истинный параллелизм, выгружая тяжелые вычисления из основного потока. Dedicated Workers обслуживают одну страницу, Shared Workers — несколько вкладок одного источника. Передача больших данных через Transferable objects (ArrayBuffer) позволяет избежать дорогостоящего копирования.

Prioritized Task Scheduling API (Scheduler API) предоставляет механизм явного управления приоритетами задач: `user-blocking` (критически важные), `user-visible` (видимые, но не критичные) и `background` (фоновые). Однако у этого API пока нет статуса Baseline: Safari не поддерживает ни `postTask()`, ни `yield()`, поэтому продакшн-код должен предусматривать fallback на `setTimeout`. Устаревший метод `isInputPending()` вытеснен современным `scheduler.yield()` и годится скорее для чтения legacy-кода, чем для новых проектов.
