# Глава 6. WebGPU — графический движок будущего

WebGPU — это современный стандарт W3C, предоставляющий веб-приложениям низкоуровневый, высокопроизводительный доступ к графическому процессору (GPU). В отличие от предшественника, WebGL, WebGPU не является портом существующего нативного API. Это API, спроектированный с нуля для эффективного взаимодействия с современными графическими бэкендами — Vulkan, Metal и Direct3D 12.

В 2026 году WebGPU действительно стал стандартом де-факто для высокопроизводительной графики и вычислений в браузере — что стоит отдельно подчеркнуть, это одна из немногих технологий в этой книге, которая уверенно достигла статуса Baseline: с января 2026 года API стабильно работает в Chrome/Edge (с 2023 года), Firefox (Windows — с версии 141, macOS на Apple Silicon — с версии 145) и Safari (с версии 26 на macOS Tahoe, iOS и iPadOS). Из практических пробелов на 2026 год остаются: Linux-сборки Firefox (в разработке), Android-версия Firefox (ожидается позже в течение года) и часть бюджетных Android-GPU с неполной поддержкой драйверов — для них по-прежнему стоит закладывать WebGL2 как fallback. Он лежит в основе 3D-игр, инженерных симуляций, видеоредакторов и нейросетевых приложений. Эта глава детально разбирает архитектуру WebGPU, его модель безопасности, работу с буферами и язык шейдеров WGSL.

## 1. Переход с WebGL на WebGPU: архитектура и безопасность

WebGL был основан на устаревшей модели OpenGL ES, которая не отражала современную архитектуру GPU и имела глобальное состояние, что усложняло разработку надежных приложений. WebGPU устраняет эти недостатки, предлагая принципиально иную архитектуру.

### 1.1. Архитектурные отличия WebGPU от WebGL

**Модель состояний.** В WebGL весь контекст рендеринга хранит множество глобальных состояний (привязанные буферы, текстуры, активные шейдеры, режимы смешивания). Это делает код хрупким и подверженным ошибкам, когда один вызов случайно изменяет состояние, ожидаемое другим участком кода. WebGPU минимизирует глобальное состояние, перенося его в объекты конвейеров и групп привязок.

**Управление ресурсами.** В WebGL буферы и текстуры могут быть изменены после создания. В WebGPU размер, формат и использование ресурсов (например, `GPUBufferUsage.STORAGE`) неизменяемы на протяжении всего жизненного цикла объекта. Это позволяет драйверу выполнять более агрессивную оптимизацию памяти и доступа.

**Управление холстом.** WebGL автоматически управляет холстом, создавая контекст, включая параметры антиалиасинга, буфера глубины и трафарета. WebGPU требует ручного управления: разработчик самостоятельно создает текстуры для рендеринга, мультисэмплинговые текстуры и выполняет разрешение (resolve) в текстуру холста. Такая гибкость позволяет выводить изображение на несколько холстов из одного устройства `GPUDevice`, что невозможно в WebGL.

**Асинхронность и многопоточность.** WebGL в основном синхронен. WebGPU спроектирован для асинхронной работы и может использоваться из Web Workers, что позволяет эффективно задействовать многоядерные процессоры для подготовки данных и команд.

**Пространство координат.** WebGPU использует начало координат текстур в верхнем левом углу (как в Metal и Direct3D), в то время как WebGL использует нижний левый угол (как в OpenGL). Z-буфер в WebGPU находится в диапазоне [0, 1], а не [-1, 1], как в WebGL.

### 1.2. Модель безопасности: защита от враждебного кода

Безопасность — ключевое требование для любого веб-стандарта. WebGPU обеспечивает многоуровневую защиту, поскольку графический стек традиционно является одной из самых атакуемых областей браузера.

**Проверка на стороне CPU.** WebGPU API спроектирован так, чтобы все операции с GPU сначала проходили строгую валидацию на CPU. Например, операция `copyBufferToBuffer()` проверяет, что буферы не пересекаются; передача невалидных данных приводит к ошибке, а не к неопределенному поведению драйвера. Это предотвращает эксплуатацию уязвимостей в драйверах через некорректные вызовы.

**Изоляция GPU-памяти.** Современные ОС позволяют изолировать адресное пространство GPU для разных процессов, что затрудняет доступ к данным другого приложения. Эта изоляция критически важна, так как предохраняет данные одного сайта от чтения вредоносным скриптом с другого сайта, даже в случае компрометации самого браузерного процесса рендеринга.

**Контроль доступа к шейдерам и буферам.** WebGPU гарантирует, что веб-страница может работать только со своими данными. Для этого шейдеры верифицируются, а доступ к буферам (даже в шейдерах) ограничивается рамками выделенной памяти. Эта мера реализуется через "robust buffer access", когда обращения вне границ либо обрезаются, либо возвращают нулевые значения.

**Многоуровневая архитектура Chrome.** В браузерах на основе Chromium стек WebGPU состоит из нескольких компонентов: Blink (JavaScript-обертка) → Dawn Wire Client (сериализация вызовов) → IPC → Dawn Wire Server (десериализация) → Dawn Native → Vulkan/Metal/Direct3D. Это добавляет дополнительный уровень проверок. Для справки: Firefox реализует WebGPU через собственный бэкенд **wgpu**, написанный на Rust и работающий поверх тех же нативных API — архитектура отличается от Dawn, но решает ту же задачу многоуровневой валидации.

**Управление таймингами.** WebGPU предоставляет низкоуровневые таймеры выполнения шейдеров, которые можно использовать для атак по сторонним каналам (timing attacks). Чтобы снизить этот риск, спецификация требует понижения точности (coarse-grained) возвращаемых значений времени, что затрудняет создание точного идентификатора устройства.

## 2. Вычисления на GPU (GPGPU) для физических симуляций и обработки изображений

Ключевое отличие WebGPU от WebGL — встроенная поддержка **вычислительных шейдеров (compute shaders)**, позволяющих выполнять массово-параллельные вычисления общего назначения (GPGPU). В WebGL подобные задачи эмулировались через хитрости с рендерингом (рендеринг в текстуру), что было неэффективно и ограничено.

### 2.1. Производительность: когда WebGPU выгоден

Исследования показывают, что WebGPU опережает WebGL и CPU для больших объемов данных, но здесь стоит быть осторожным с конкретными цифрами — в материалах про WebGPU часто путают два принципиально разных сравнения: «WebGPU против WebGL» и «WebGPU против CPU/WASM», а разница в порядках величины между ними существенная.

**Для малых входных данных** накладные расходы на инициализацию WebGPU, компиляцию шейдеров и синхронизацию CPU-GPU могут делать его медленнее, чем выполнение на CPU. WebGL может быть быстрее WebGPU для малых данных из-за более низкого начального оверхеда.

**Для больших входных данных** WebGPU значительно опережает CPU благодаря эффективному использованию тысяч ядер GPU. Параллельные алгоритмы показывают значительный прирост производительности.

**Циклические алгоритмы.** WebGPU показывает лучшую производительность для алгоритмов с интенсивным циклом, требующим частого обмена данными между CPU и GPU. WebGPU минимизирует такие обмены.

**Реалистичные цифры именно для сравнения WebGL vs WebGPU** (а не против CPU): актуальные бенчмарки показывают ускорение порядка **3–8×** для операций матричного умножения (GEMM) на больших матрицах (от 2048×2048 и выше) — за счёт нативных вычислительных шейдеров, storage-буферов и разделяемой памяти рабочих групп, недоступных в WebGL. Для инференса трансформерных моделей через ONNX Runtime Web типичный прирост от перехода с WebGL на WebGPU составляет **3–5×**; более впечатляющие цифры (25–35× и выше), которые можно встретить в отдельных бенчмарках, как правило, относятся к сравнению WebGPU с CPU-инференсом через WASM, а не с WebGL — эти два сценария не стоит путать при планировании архитектуры. Конкретная цифра в любом случае сильно зависит от производителя GPU, архитектуры модели и версии браузера, так что относитесь к любому проценту ускорения как к ориентиру порядка величины, а не к гарантии.

### 2.2. Применение GPGPU на WebGPU

**Физические симуляции.** Моделирование частиц, жидкостей, тканей и столкновений. Тысячи частиц могут быть независимо обновлены в каждом кадре.

**Обработка изображений и видео.** Фильтры (размытие, резкость, цветокоррекция), нейросетевая обработка (удаление фона, раскрашивание).

**Трассировка лучей.** Вычислительные шейдеры могут обрабатывать трассировку миллионов лучей параллельно.

**Научные вычисления.** Обработка больших массивов, симуляции, анализ данных.

**Машинное обучение.** WebGPU лежит в основе многих браузерных реализаций нейросетей (через ONNX Runtime Web, TensorFlow.js, transformers.js), обеспечивая приемлемую производительность для инференса — и, как отмечалось во Введении, именно этот стек (а не WebNN) остаётся практическим путём для браузерного ML в 2026 году.

### 2.3. Практический пример: вычисление суммы элементов

```javascript
// Создание вычислительного конвейера
const computePipeline = device.createComputePipeline({
    layout: device.createPipelineLayout({
        bindGroupLayouts: [device.createBindGroupLayout({
            entries: [
                { binding: 0, visibility: GPUShaderStage.COMPUTE, buffer: { type: 'storage' } },
                { binding: 1, visibility: GPUShaderStage.COMPUTE, buffer: { type: 'storage' } }
            ]
        })]
    }),
    compute: {
        module: device.createShaderModule({
            code: `
                @group(0) @binding(0) var<storage, read> input: array<f32>;
                @group(0) @binding(1) var<storage, read_write> output: array<f32>;

                @compute @workgroup_size(64)
                fn main(@builtin(global_invocation_id) id: vec3<u32>) {
                    let idx = id.x;
                    if (idx < arrayLength(&input)) {
                        // Атомарное суммирование
                        atomicAdd(&output[0], input[idx]);
                    }
                }
            `
        }),
        entryPoint: 'main'
    }
});

// Выполнение
const commandEncoder = device.createCommandEncoder();
const pass = commandEncoder.beginComputePass();
pass.setPipeline(computePipeline);
pass.setBindGroup(0, bindGroup);
pass.dispatchWorkgroups(Math.ceil(dataSize / 64));
pass.end();
device.queue.submit([commandEncoder.finish()]);
```

## 3. Работа с буферами и шейдерами (WGSL)

### 3.1. Буферы WebGPU

WebGPU управляет памятью через объекты `GPUBuffer`. Буфер — это непрерывный блок памяти на GPU, который может использоваться как источник данных для шейдеров, как приемник результатов или как промежуточное хранилище.

**Создание буфера:**

```javascript
const buffer = device.createBuffer({
    size: 1024, // размер в байтах, должен быть кратен 4 
    usage: GPUBufferUsage.STORAGE | GPUBufferUsage.COPY_DST,
    mappedAtCreation: false
});
```

**Типы использования буферов (`GPUBufferUsage`):**

- **`STORAGE`.** Буфер для чтения и записи в вычислительных и вершинных шейдерах. Гарантированный минимум по спецификации — 128 МБ (`maxStorageBufferBindingSize`), но на практике многие десктопные реализации предоставляют значительно больше (вплоть до нескольких ГБ на дискретных GPU) — точное значение стоит запрашивать через `adapter.limits`, а не считать фиксированным.
- **`UNIFORM`.** Буфер только для чтения, доступный шейдерам. Ограничен по размеру — 64 КБ по умолчанию (`maxUniformBufferBindingSize`).
- **`VERTEX`.** Буфер для вершинных атрибутов.
- **`INDEX`.** Буфер для индексов вершин.
- **`COPY_DST` / `COPY_SRC`.** Буфер, используемый как источник или приемник для операций копирования.

**Различия между Uniform и Storage буферами:**

| Характеристика | Uniform буфер | Storage буфер |
|----------------|---------------|---------------|
| **Минимальный гарантированный размер по спецификации** | 64 КБ | 128 МБ (на практике часто больше — до нескольких ГБ на десктопных дискретных GPU) |
| **Доступ** | Только чтение | Чтение/запись |
| **Производительность** | Быстрее для типичных сценариев | Медленнее, но гибче |
| **Использование** | Матрицы трансформации, параметры материалов | Массивы данных большого размера, результаты вычислений |

**Запись данных в буфер:**

```javascript
// Через queue.writeBuffer (синхронно, для небольших данных)
const data = new Float32Array([1.0, 2.0, 3.0, 4.0]);
device.queue.writeBuffer(buffer, 0, data);

// Через маппинг (для больших данных, асинхронно)
await buffer.mapAsync(GPUMapMode.WRITE);
const mapped = new Float32Array(buffer.getMappedRange());
mapped.set(data);
buffer.unmap();
```

**Проверка реальных лимитов устройства перед выделением больших буферов:**

```javascript
const adapter = await navigator.gpu.requestAdapter();
console.log('Реальный лимит storage-буфера на этом устройстве:', adapter.limits.maxStorageBufferBindingSize);
// На мобильных GPU это может быть близко к гарантированному минимуму (128 МБ),
// на десктопных дискретных картах — значительно больше. Не полагайтесь на одно число для всех устройств.
```

### 3.2. WGSL (WebGPU Shading Language)

WGSL — это язык программирования шейдеров для WebGPU. Его синтаксис ближе к Rust, чем к C (как в GLSL), и он разработан так, чтобы быть надежным и легко верифицируемым.

**Пример WGSL-шейдера (вершинный и фрагментный):**

```wgsl
// Структура для передачи данных между этапами
struct VertexOutput {
    @builtin(position) position: vec4f,
    @location(0) color: vec4f,
};

// Входные данные: атрибуты вершины
struct VertexAttributes {
    @location(0) position: vec3f,
    @location(1) color: vec3f,
};

// Группа привязки 0: uniform-буфер с матрицей трансформации
@group(0) @binding(0) var<uniform> transform: mat4x4f;

// Вершинный шейдер
@vertex
fn vs_main(in: VertexAttributes) -> VertexOutput {
    var out: VertexOutput;
    out.position = transform * vec4f(in.position, 1.0);
    out.color = vec4f(in.color, 1.0);
    return out;
}

// Фрагментный шейдер
@fragment
fn fs_main(in: VertexOutput) -> @location(0) vec4f {
    return in.color;
}
```

**Пример вычислительного шейдера:**

```wgsl
// Входной и выходной буферы
@group(0) @binding(0) var<storage, read> input: array<f32>;
@group(0) @binding(1) var<storage, read_write> output: array<f32>;

// Определение размера рабочей группы
@compute @workgroup_size(64)
fn main(@builtin(global_invocation_id) id: vec3u) {
    let index = id.x;
    if (index < arrayLength(&input)) {
        // Пример: умножаем каждый элемент на 2
        output[index] = input[index] * 2.0;
    }
}
```

**Ключевые особенности WGSL:**

- **Строгая типизация.** WGSL статически типизирован, и все переменные должны быть явно объявлены.
- **Встроенные атрибуты.** Используются атрибуты `@builtin`, `@location`, `@group`, `@binding` для связывания с данными.
- **Нет неопределенного поведения.** WGSL определен так, чтобы исключить неопределенное поведение, упрощая валидацию.
- **Поддержка атомарных операций.** Необходима для корректной синхронизации доступа к shared-памяти и storage-буферам.

## Итог

WebGPU — это фундаментальный стандарт, заменивший устаревший WebGL в качестве основного API для доступа к GPU в вебе. Он предоставляет низкоуровневый, безопасный и производительный интерфейс к современным графическим бэкендам — и один из немногих в этой книге примеров технологии, полностью достигшей статуса Baseline к 2026 году (с оговоркой на Linux/Android-хвост Firefox).

- **Архитектура.** WebGPU устраняет глобальное состояние WebGL, предлагая четкую модель объектов (устройство, очередь, конвейеры, группы привязок). Он поддерживает асинхронность, многопоточность и ручное управление ресурсами.
- **Безопасность.** WebGPU внедряет многоуровневую защиту: валидацию на CPU, изоляцию GPU-памяти, верификацию шейдеров, контроль доступа к буферам и защиту от атак по времени.
- **Вычисления (GPGPU).** Вычислительные шейдеры WebGPU обеспечивают массово-параллельные вычисления. Для больших данных WebGPU значительно опережает CPU и WebGL — реалистично рассчитывайте на 3–8× для GEMM-операций и 3–5× для инференса трансформеров при сравнении именно с WebGL, а не с CPU/WASM.
- **WGSL.** Язык шейдеров WGSL, с синтаксисом, близким к Rust, статически типизирован и разработан для надежности и простоты валидации.

В следующей главе мы рассмотрим WebNN API — стандарт для выполнения нейросетевых моделей с аппаратным ускорением (NPU/TPU), уже подробно описанный во Введении как экспериментальная, пока не готовая к продакшну технология.
