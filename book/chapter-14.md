# Глава 14. Chrome DevTools 2026: Профилирование системного уровня

В 2026 году Chrome DevTools эволюционировал в полноценную среду для системного профилирования, выйдя далеко за рамки простого инспектирования DOM и отладки JavaScript. Современные DevTools предоставляют разработчикам инструменты для анализа активности GPU и Worker'ов, поиска утечек памяти в SharedArrayBuffers и автоматизации тестирования производительности через Recorder нового поколения. Эта глава последовательно разбирает три ключевых инструмента: панель Performance с её возможностями низкоуровневого профилирования, панель Memory с техниками поиска утечек, и Recorder как средство автоматизации тестирования.

---

## 1. Панель Performance: анализ активности потоков GPU и Worker'ов

Панель Performance в Chrome DevTools 2026 года представляет собой мощный инструмент для анализа времени выполнения всех компонентов браузера . В отличие от более ранних версий, современная панель позволяет профилировать не только основной поток, но и фоновые процессы — GPU и Web Workers.

### 1.1. Подготовка к профилированию

Для получения точных результатов профилирования рекомендуется запускать тесты в режиме инкогнито, так как расширения браузера могут искажать результаты измерений . Это особенно важно при анализе активности GPU и Worker'ов, где влияние сторонних расширений может быть значительным.

### 1.2. Профилирование основного потока

При записи профиля (нажатие кнопки Record) панель Performance собирает детальные данные о:

- Выполнении JavaScript (включая JIT-компиляцию)
- Вычислениях Layout и Paint
- Работе сборщика мусора
- Сетевых запросах и их влиянии на рендеринг

Временная шкала позволяет визуализировать длительные задачи (Long Tasks) — задачи, выполняющиеся более 50 мс и блокирующие основной поток . Каждая задача маркируется цветом: желтые блоки обозначают выполнение JavaScript, фиолетовые — Layout и Paint, зеленые — работу сборщика мусора.

### 1.3. Профилирование потоков GPU

Современный браузер выносит все операции с графическим процессором в отдельный **GPU Process** (см. Главу 1). Панель Performance 2026 года позволяет анализировать активность этого процесса:

- Временные метки выполнения шейдеров
- Операции композитинга (наложение слоев)
- Работу с текстурами и буферами
- Загрузку GPU при отрисовке сложных анимаций и WebGL/WebGPU-сцен

На временной шкале появляется отдельный трек для GPU, где отображаются периоды активности графического процессора. Если приложение использует WebGPU для вычислений (см. Главу 6), этот трек показывает нагрузку на GPU от вычислительных шейдеров.

### 1.4. Профилирование Web Workers

Web Workers выполняются в отдельных потоках, изолированных от основного потока рендеринга. Панель Performance 2026 года позволяет профилировать их отдельно:

- Отображение выполнения кода внутри Dedicated и Shared Workers
- Время выполнения задач в воркерах
- Операции postMessage и обмен данными с основным потоком
- Загрузку CPU каждым воркером

На временной шкале появляются отдельные треки для каждого активного воркера. Это позволяет выявить ситуации, когда Worker перегружен вычислениями и не успевает обрабатывать сообщения от основного потока, создавая задержки в INP (Interaction to Next Paint).

### 1.5. Полезные функции Chrome 145–146

В версиях Chrome 145–146 были добавлены следующие возможности для профилирования :

- **Soft navigation traces** — отслеживание "мягких" навигаций в SPA через Navigation API
- **Precise line-level profiling** — профилирование с точностью до строки кода
- **Render-blocking network column** — отображение сетевых ресурсов, блокирующих рендеринг, в виде отдельной колонки в таблице запросов

## 2. Панель Memory: поиск утечек в SharedArrayBuffers

Панель Memory — это основной инструмент для диагностики проблем с памятью в веб-приложениях. В 2026 году она получила поддержку отладки SharedArrayBuffers, что критически важно для приложений, использующих многопоточность через Web Workers и WebAssembly.

### 2.1. Типичные причины утечек памяти

Перед тем как перейти к инструментам, важно понимать, что может вызывать утечки памяти в современных приложениях :

- **Глобальные переменные.** Непреднамеренное создание глобальных переменных (например, из-за пропущенного `var`, `let` или `const` в строгом режиме, который не работает в некоторых контекстах)
- **Неудаленные обработчики событий.** Слушатели событий, не удаленные при размонтировании компонентов
- **Замыкания.** Замыкания, удерживающие ссылки на большие объекты в памяти
- **Отсоединенные DOM-узлы.** DOM-элементы, удаленные из документа, но все еще доступные через ссылки в JavaScript
- **Таймеры.** Таймеры (`setTimeout`, `setInterval`), не отмененные после завершения работы
- **Неограниченные коллекции.** Карты и массивы (Map, Set, Array), в которые бесконечно добавляются данные без удаления старых записей

### 2.2. Heap Snapshot: точка во времени

**Heap Snapshot** — это снимок распределения памяти в определенный момент времени . Он позволяет увидеть, какие объекты занимают память, как они связаны между собой и откуда на них есть ссылки.

**Для создания снимка:**

1. Открыть панель Memory в DevTools
2. Выбрать тип "Heap snapshot"
3. Нажать кнопку "Take snapshot"
4. Дождаться завершения захвата (индикатор прогресса исчезнет)

**Ключевые метрики при просмотре снимка :**

- **Shallow Size** — память, занимаемая непосредственно объектом (без учета ссылок на другие объекты)
- **Retained Size** — общая память, которая будет освобождена при удалении объекта (включая все объекты, на которые он ссылается)
- **Distance** — расстояние от корневого объекта GC (сборщика мусора) до текущего объекта

### 2.3. Сравнение снимков для поиска утечек

Основной метод поиска утечек — сравнение двух снимков, сделанных в разные моменты времени :

1. Сделать первый снимок до выполнения подозрительных действий
2. Выполнить действия (например, открыть и закрыть модальное окно, перейти на другую страницу)
3. Сделать второй снимок
4. В панели Memory переключиться из режима "Summary" в режим "Comparison"
5. Проанализировать объекты, которые были добавлены, но не удалены

В режиме сравнения отображаются:

- Объекты, появившиеся между снимками (New)
- Объекты, удаленные между снимками (Deleted)
- Объекты, у которых изменился размер (Changed)

**На что обращать внимание при анализе сравнений :**

- **Отсоединенные DOM-деревья (Detached DOM trees)** — узлы, удаленные из документа, но все еще хранящиеся в памяти из-за ссылок в JavaScript
- **Растущие коллекции** — массивы или Map, которые продолжают расти между снимками
- **Увеличивающееся число ретейнеров** — объекты, на которые ссылается все больше других объектов

### 2.4. Поиск утечек в SharedArrayBuffers

Современные приложения, использующие многопоточность через Web Workers и WebAssembly, часто применяют SharedArrayBuffers для обмена данными между потоками. В 2026 году панель Memory позволяет отлаживать утечки в этих буферах:

1. После захвата Heap Snapshot в строке поиска ввести `SharedArrayBuffer`
2. Расширить результаты для просмотра всех экземпляров SharedArrayBuffer в памяти
3. Проверить, какие воркеры или WASM-модули удерживают ссылки на буферы
4. Проанализировать, освобождаются ли буферы после завершения работы воркеров

**Типичные сценарии утечек SharedArrayBuffers:**

- Воркер не завершен (`worker.terminate()` не вызван), и буфер остается в памяти
- WASM-модуль удерживает ссылку на буфер после завершения работы
- Несколько воркеров используют один буфер, и ни один из них не освобождает его явно

### 2.5. Allocation Timeline: динамический анализ

Помимо статического Heap Snapshot, панель Memory предоставляет **Allocation timeline** (выделение памяти на временной шкале) :

1. Выбрать "Allocation instrumentation on timeline" в панели Memory
2. Нажать кнопку записи
3. Выполнить действия в приложении (например, прокрутка страницы, загрузка данных)
4. Остановить запись

Визуализация показывает синие столбцы — объекты, которые остались в памяти (потенциальные утечки), и серые столбцы — объекты, которые были собраны сборщиком мусора. Если синие столбцы появляются в зоне, где вы ожидаете очистки памяти, это указывает на утечку.

### 2.6. DevTools для агентов: отладка памяти в автоматизации

В версии Chrome 150 была представлена новая возможность: **DevTools для агентов** с экспериментальным режимом отладки памяти (`--experimentalMemory`) . Этот режим позволяет агентам захватывать и анализировать V8 heap snapshots непосредственно для диагностики утечек памяти и анализа иерархий удержания объектов в автоматизированных тестах . Эта функция особенно полезна при интеграции с MCP-сервером DevTools, который был представлен в Chrome 144 .

## 3. Recorder нового поколения: автоматизация тестирования производительности

Chrome Recorder — это встроенный инструмент для записи и воспроизведения пользовательских сценариев в браузере. В 2026 году он стал полноценным средством для автоматизации тестирования производительности, позволяя разработчикам записывать сложные пользовательские потоки, воспроизводить их и анализировать производительность.

### 3.1. Запись пользовательского потока

Recorder позволяет записывать последовательность действий пользователя на странице без написания кода :

1. Открыть DevTools, найти Recorder в панели More tools или через кнопку "⋮" → More tools → Recorder
2. Нажать "+ New recording" и дать название потоку (например, "Поиск-фильтр-детали")
3. Нажать "Start recording"
4. Выполнить действия в браузере: клики, ввод текста, навигация
5. Нажать "Stop recording" после завершения сценария

Recorder фиксирует каждый шаг: тип действия (click, navigate, input), селекторы элементов, введенные данные, координаты клика . Это позволяет точно воспроизводить поведение пользователя.

### 3.2. Воспроизведение с профилированием производительности

Ключевая особенность Recorder 2026 года — возможность воспроизводить записанные сценарии и одновременно измерять производительность, что автоматизирует процесс нагрузочного тестирования :

1. Переключиться на панель Performance
2. Нажать кнопку Record в панели Performance
3. Переключиться на Recorder и нажать Replay для воспроизведения записанного сценария
4. Выбрать скорость воспроизведения (нормальная, медленная, очень медленная) для более точного анализа временной шкалы
5. После завершения воспроизведения остановить запись в Performance

Полученный профиль содержит полную временную шкалу всех событий, связанных с действиями пользователя. Анализ временной шкалы позволяет выявить узкие места:

- **Навигация с длительным белым экраном** → проверить Network трек на время загрузки HTML, затем проверить, есть ли длительное выполнение JavaScript после загрузки
- **Клик без ответа** → найти в треке событие click, посмотреть, что следует за ним: Forced Synchronous Layout (фиолетовый с предупреждением) или длительная задача (желтый)
- **Задержка ввода** → в треке найти событие input или change, измерить время выполнения обработчиков; если превышает 16 мс, это приводит к пропуску кадров
- **Дергающаяся прокрутка** → в панели Rendering включить FPS meter и проверить падение FPS во время прокрутки в Recorder

### 3.3. Экспорт и интеграция с Puppeteer

Recorder позволяет экспортировать записанные сценарии в форматы, пригодные для автоматизации :

1. В Recorder нажать кнопку "⋮" (меню)
2. Выбрать "Export" → "Puppeteer"
3. Полученный JavaScript-код можно использовать в среде Puppeteer

В этом коде автоматически добавлены `performance.mark()` и `performance.measure()` для измерения производительности каждого шага сценария . Это позволяет:

- Запускать автоматизированные тесты производительности в CI/CD
- Сравнивать производительность между разными версиями приложения
- Проводить нагрузочное тестирование с различными сетевыми условиями

### 3.4. Редактирование сценариев

Recorder позволяет редактировать записанные сценарии вручную :

- Добавлять шаги между существующими
- Удалять шаги
- Изменять селекторы и значения
- Добавлять паузы (`waitFor`) для синхронизации с асинхронными операциями

Это полезно, когда записанный сценарий содержит лишние или неверные шаги.

## Итог

Chrome DevTools 2026 года предоставляет три взаимосвязанных инструмента для профилирования и оптимизации веб-приложений:

- **Панель Performance** позволяет анализировать активность основного потока, GPU и Web Workers. Она поддерживает профилирование с точностью до строки кода, обнаружение блокирующих рендеринг ресурсов и трассировку мягких навигаций в SPA.
- **Панель Memory** предоставляет механизмы для поиска утечек памяти через Heap Snapshot и Allocation Timeline. Сравнение снимков позволяет выявлять объекты, которые не освобождаются при выполнении пользовательских действий. В 2026 году добавлена поддержка отладки SharedArrayBuffers и DevTools for agents с экспериментальным режимом отладки памяти.
- **Recorder нового поколения** позволяет записывать пользовательские потоки, воспроизводить их с профилированием производительности и экспортировать в Puppeteer для автоматизации тестирования.
