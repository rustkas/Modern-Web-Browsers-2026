# Глава 12. Модель изоляции и Permissions API

В 2026 году безопасность и приватность стали фундаментальными принципами архитектуры браузера как мета-ОС. Современный браузер предоставляет многоуровневую модель изоляции, которая защищает данные пользователя, предотвращает несанкционированный доступ к аппаратным ресурсам и обеспечивает соблюдение регуляторных требований (GDPR, CCPA). Эта глава рассматривает три ключевых аспекта модели безопасности браузера 2026 года: тонкое управление разрешениями через Permissions API, технологию Private State Tokens для борьбы с фродом без отслеживания пользователей и Federated Credential Management (FedCM) для безопасной аутентификации без сторонних кук.

---

## 1. Тонкая настройка прав: Permissions API

Permissions API предоставляет унифицированный интерфейс для запроса, проверки и отслеживания статуса прав доступа к функциям устройства и браузерным возможностям. В 2026 году этот API стал стандартным механизмом управления разрешениями во всех современных браузерах.

### 1.1. Модель разрешений

Браузерная модель разрешений основана на трех состояниях :

- **`granted`** — разрешение предоставлено пользователем. Приложение может использовать соответствующую функцию.
- **`denied`** — разрешение отклонено пользователем. Приложение не может использовать функцию, и браузер не будет повторно запрашивать разрешение.
- **`prompt`** — разрешение еще не запрашивалось. При вызове API браузер покажет диалог запроса разрешения.

**Важное различие:** Разрешения могут быть отклонены "навсегда" (`denied`) или временно. В случае постоянного отказа (`isPermanentlyDenied`) приложение может предложить пользователю перейти в настройки браузера для ручного изменения разрешения через `openAppSettings()` .

### 1.2. Основные типы разрешений в 2026 году

Современные браузеры поддерживают широкий спектр разрешений :

| Тип разрешения | Описание |
|----------------|----------|
| **`camera`** | Доступ к камере устройства |
| **`microphone`** | Доступ к микрофону |
| **`geolocation`** | Доступ к геолокации |
| **`notifications`** | Показ push-уведомлений |
| **`clipboard-read`** | Чтение буфера обмена |
| **`clipboard-write`** | Запись в буфер обмена |
| **`storage`** | Доступ к постоянному хранилищу |
| **`sensors`** | Доступ к датчикам движения |

### 1.3. Практическое использование Permissions API

**Проверка статуса разрешения:**

```javascript
// Проверка статуса разрешения на камеру
async function checkCameraPermission() {
    const status = await navigator.permissions.query({ name: 'camera' });
    
    console.log(`Статус: ${status.state}`); // 'granted', 'denied', 'prompt'
    
    // Отслеживание изменений статуса
    status.addEventListener('change', () => {
        console.log(`Статус изменился: ${status.state}`);
        // Адаптация UI в зависимости от нового статуса
    });
    
    return status;
}
```

**Запрос разрешения на множественные функции:**

```javascript
// Запрос разрешений на камеру и микрофон
async function requestMediaPermissions() {
    try {
        // Запрос через MediaDevices API автоматически триггерит запрос разрешений
        const stream = await navigator.mediaDevices.getUserMedia({
            video: true,
            audio: true
        });
        
        // После получения доступа проверяем статус
        const cameraStatus = await navigator.permissions.query({ name: 'camera' });
        const micStatus = await navigator.permissions.query({ name: 'microphone' });
        
        return {
            camera: cameraStatus.state === 'granted',
            microphone: micStatus.state === 'granted'
        };
    } catch (error) {
        console.error('Доступ к медиа-устройствам отклонен:', error);
        return { camera: false, microphone: false };
    }
}
```

### 1.4. Обработка постоянного отказа

Если пользователь навсегда отклонил разрешение, приложение должно корректно обработать эту ситуацию :

```javascript
async function handlePermissionRequest() {
    const status = await navigator.permissions.query({ name: 'geolocation' });
    
    if (status.state === 'denied') {
        // Проверяем, является ли отказ постоянным
        if (status.isPermanentlyDenied) {
            // Показываем сообщение и направляем пользователя в настройки
            showMessage('Разрешение на геолокацию навсегда отклонено. ' +
                       'Вы можете изменить это в настройках браузера.');
            
            // Открываем настройки браузера (поддерживается не во всех браузерах)
            if (navigator.permissions.openAppSettings) {
                await navigator.permissions.openAppSettings();
            }
        } else {
            // Временный отказ — можно попробовать запросить снова
            showMessage('Разрешение на геолокацию необходимо для работы приложения.');
        }
    }
}
```

### 1.5. Группы разрешений

В 2026 году браузеры поддерживают группировку разрешений для упрощения управления. Например, разрешения `camera` и `microphone` часто запрашиваются вместе, и браузер может показывать единый диалог для обоих.

## 2. Private State Tokens: борьба с фродом без кук

Private State Tokens (ранее называвшиеся Trust Tokens) — это API, который позволяет сайтам передавать ограниченные приватные сигналы о доверии к пользователю между разными контекстами без использования идентифицирующих файлов cookie .

### 2.1. Мотивация

Веб-экосистема сильно зависит от сигналов доверия для обнаружения мошеннических и спам-действий. Традиционно это делалось через отслеживание активности браузера с использованием стабильных идентификаторов. Private State Tokens решают эту проблему, предоставляя механизм, который позволяет сегментировать пользователей на "доверенных" и "недоверенных" без создания глобального идентификатора пользователя .

**Ключевое свойство:** Токены не персонализированы и не могут быть использованы для отслеживания пользователей. Они криптографически подписаны, что предотвращает их подделку .

### 2.2. Архитектура Private State Tokens

API работает на основе протокола Privacy Pass и использует три основные операции :

**1. Issuance (Выпуск токенов).** Когда origin доверяет пользователю (например, после успешного входа или прохождения капчи), он может выпустить пакет токенов:

```javascript
fetch('https://issuer.example/issue', {
    privateToken: {
        version: 1,
        operation: 'token-request'
    }
});
```

Браузер генерирует набор nonce (случайных чисел), "ослепляет" их (blinding — криптографическая техника, скрывающая данные) и отправляет на сервер. Сервер подписывает их и возвращает. Браузер "снимает ослепление" и сохраняет пары (nonce + подпись). **Сырые токены никогда не доступны JavaScript** — они хранятся и управляются исключительно браузером .

**2. Redemption (Погашение токенов).** Когда пользователь посещает другой сайт, этот сайт может запросить погашение токенов:

```javascript
// Проверка наличия токенов
const hasToken = await document.hasPrivateToken('https://issuer.example');

if (hasToken) {
    fetch('https://issuer.example/redeem', {
        privateToken: {
            version: 1,
            operation: 'token-redemption',
            refreshPolicy: 'none' // или 'refresh'
        }
    });
}
```

Если токены есть, браузер использует протокол Privacy Pass для погашения токена. Сервер проверяет подпись и может вернуть **Redemption Record (RR)** — запись о погашении, которая кешируется браузером .

**3. Forwarding Redemption Attestation (Пересылка аттестации).** RR могут быть переданы третьим сторонам через Fetch API:

```javascript
fetch('https://publisher.example/api', {
    privateToken: {
        version: 1,
        operation: 'send-redemption-record',
        issuers: ['https://issuer.example']
    }
});
```

RR добавляются в HTTP-заголовок `Sec-Redemption-Record`. Заголовок HTTP-only, доступ к RR через JavaScript невозможен напрямую .

### 2.3. Криптографические гарантии приватности

**Свойство Unlinkability (Невозможность связывания)** — ключевая гарантия приватности :

- Выпуск токенов **не может быть связан** с их погашением.
- Эмитент не может коррелировать выпуск токенов на одном сайте с их погашением на другом.
- Эмитент узнает только агрегированную информацию о том, какие сайты посещают пользователи, но не может связать это с конкретной личностью.

**Технические меры для защиты свойства Unlinkability** :

- **Key Consistency.** Сервер не может использовать разные приватные ключи для разных клиентов, что предотвратило бы деанонимизацию. Протокол требует публикации списка публичных ключей (не более 3 ключей) и верификации консистентности.
- **Защита от fingerprinting.** API не раскрывает новой информации, которую злоумышленники не могли бы получить через другие механизмы (например, через сетевые запросы).

### 2.4. Ограничения и лимиты

Чтобы предотвратить злоупотребления и утечку идентификационной информации, API имеет строгие ограничения :

- **Per-Site Issuer Limits.** Количество эмитентов токенов на один top-level origin жестко ограничено (например, не более 2). Это предотвращает использование большого количества эмитентов для создания канала передачи идентификационной информации.
- **Rate Limiting на Redemption.** Эмитенты могут ограничивать частоту погашения токенов, возвращая кешированные RR (Redemption Records) при слишком частых попытках.
- **Lifetime RR.** Время жизни RR ограничено либо через заголовок `Sec-Private-State-Token-Lifetime`, либо привязано к времени жизни ключа верификации .

## 3. Federated Credential Management (FedCM): вход без сторонних кук

Federated Credential Management API (FedCM) — это стандарт, предоставляющий механизм для федеративной аутентификации (например, "Войти через Google/Facebook") без использования сторонних cookies и навигационных редиректов .

### 3.1. Проблема традиционной федеративной аутентификации

Традиционные механизмы федеративной аутентификации полагаются на **iframes, редиректы и сторонние cookies** . Это создает проблемы:

- **Приватность.** Браузеры не могут отличить легитимные сервисы идентификации от нежелательного отслеживания. Третьи стороны могут использовать эти механизмы для отслеживания пользователей по всей сети .
- **Ограничение сторонних cookies.** Современные браузеры ограничивают использование сторонних cookies, что ломает традиционные федеративные потоки .
- **Неконсистентный UX.** Сайты отображают большое количество кнопок входа (NASCAR problem), что загромождает интерфейс .

### 3.2. Как работает FedCM

FedCM предоставляет **браузерно-опосредованный UI** для выбора аккаунта и входа . Вместо того чтобы сайт отображал кнопки входа, браузер показывает стандартизированный диалог выбора аккаунта.

**Два режима UI** :

- **Пассивный (Passive) режим.** Диалог появляется автоматически при загрузке страницы, если пользователь уже вошел в систему у Identity Provider (IdP).
- **Активный (Active) режим.** Диалог появляется только после действия пользователя (например, клика по кнопке "Войти").

**Базовый код входа через FedCM:**

```javascript
async function signInWithFedCM() {
    try {
        const credential = await navigator.credentials.get({
            identity: {
                providers: [{
                    configURL: 'https://accounts.idp.example/config.json',
                    clientId: 'rp-client-id',
                    nonce: 'some-random-nonce'
                }]
            }
        });
        
        // credential содержит информацию о выбранном аккаунте
        console.log('Авторизация успешна:', credential);
        
        // Отправка токена на сервер RP
        await sendTokenToServer(credential);
    } catch (error) {
        if (error.name === 'AbortError') {
            console.log('Пользователь отменил вход');
        } else {
            console.error('Ошибка входа:', error);
        }
    }
}
```

### 3.3. Преимущества FedCM

**Поддержка без сторонних cookies.** FedCM работает даже в режиме инкогнито и когда сторонние cookies отключены . Он интегрирован с другими Privacy Sandbox API — например, Storage Access API использует FedCM как сигнал доверия .

**Улучшенный UX.** Вместо множества кнопок входа FedCM показывает браузерный диалог с аккаунтами, отфильтрованными по релевантности: сначала показываются аккаунты, недавно использовавшиеся на устройстве, затем аккаунты, уже использовавшиеся на RP, и только потом новые аккаунты .

**Безопасность.** FedCM снижает поверхность для фишинга, так как пользователь использует управляемые IdP аккаунты вместо создания новых паролей для каждого сайта. RP может полагаться на экспертизу IdP в области безопасного управления идентификацией .

**Поддержка множественных IdP.** FedCM позволяет сайту поддерживать несколько Identity Providers без загромождения UI. Пользователи могут выбирать предпочтительного провайдера независимо от его размера .

### 3.4. Сравнение: Традиционный вход vs FedCM

| Аспект | Традиционный вход | FedCM |
|--------|------------------|-------|
| **Сторонние cookies** | Требуются | Не требуются |
| **UI** | Управляется RP (кнопки) | Браузерный диалог |
| **Блокировка трекеров** | Часто блокируется | Не блокируется |
| **Работа в инкогнито** | Может не работать | Работает |
| **Поддержка IdP** | Любой с cookies | Требует реализации FedCM |
| **Приватность** | Потенциальные утечки | Встроенная защита |

### 3.5. Кто должен использовать FedCM

FedCM полезен для :
- **Identity Providers (IdP).** Чтобы предлагать бескукенную аутентификацию своим клиентам.
- **Relying Parties (RP)** с множеством IdP-интеграций (более 4 провайдеров), особенно когда они хотят поддерживать вход для пользователей, отключивших сторонние cookies.
- **Сайты с высокими требованиями к конфиденциальности,** которые хотят избежать использования технологий, связанных с отслеживанием.

## Итог

Модель изоляции и разрешений браузера 2026 года — это трехкомпонентная система, обеспечивающая безопасность и приватность пользователей:

- **Permissions API** предоставляет унифицированный интерфейс для управления доступом к функциям устройства и браузера. Поддерживает три состояния (`granted`, `denied`, `prompt`), позволяет отслеживать изменения статуса и корректно обрабатывать постоянные отказы.
- **Private State Tokens** (ранее Trust Tokens) — криптографический механизм для борьбы с фродом и спамом без использования идентифицирующих файлов cookie. Основан на протоколе Privacy Pass и гарантирует невозможность связывания выпуска и погашения токенов. RR (Redemption Records) кешируются браузером и могут быть переданы третьим сторонам через HTTP-заголовки.
- **Federated Credential Management (FedCM)** — стандарт для федеративной аутентификации без сторонних cookies и редиректов. Предоставляет браузерно-опосредованный UI для выбора аккаунта, работает в режиме инкогнито, интегрирован с другими Privacy Sandbox API и поддерживает множественные Identity Providers.

В следующей главе мы рассмотрим защиту от цифровых отпечатков (Fingerprinting) и новые механизмы клиентских подсказок (Client Hints).
