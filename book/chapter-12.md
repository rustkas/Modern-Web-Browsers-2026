# Глава 12. Модель изоляции и Permissions API

В 2026 году безопасность и приватность стали фундаментальными принципами архитектуры браузера как мета-ОС. Современный браузер предоставляет многоуровневую модель изоляции, которая защищает данные пользователя, предотвращает несанкционированный доступ к аппаратным ресурсам и обеспечивает соблюдение регуляторных требований (GDPR, CCPA). Эта глава рассматривает три ключевых аспекта модели безопасности браузера 2026 года: тонкое управление разрешениями через Permissions API, технологию Private State Tokens для борьбы с фродом без отслеживания пользователей и Federated Credential Management (FedCM) для безопасной аутентификации без сторонних кук. Забегая вперёд: если Permissions API — зрелая, полностью кросс-браузерная технология, то у FedCM и Private State Tokens сохраняются существенные ограничения по поддержке, которые важно понимать перед проектированием архитектуры.

---

## 1. Тонкая настройка прав: Permissions API

Permissions API предоставляет унифицированный интерфейс для запроса, проверки и отслеживания статуса прав доступа к функциям устройства и браузерным возможностям. `navigator.permissions` достиг статуса Baseline (широко доступен) ещё в сентябре 2022 года и одинаково работает во всех современных браузерах.

### 1.1. Модель разрешений

Браузерная модель разрешений основана на трех состояниях `PermissionStatus.state`:

- **`granted`** — разрешение предоставлено пользователем. Приложение может использовать соответствующую функцию.
- **`denied`** — разрешение отклонено пользователем. Приложение не может использовать функцию, и браузер не будет повторно запрашивать разрешение автоматически.
- **`prompt`** — разрешение еще не запрашивалось. При вызове API браузер покажет диалог запроса разрешения.

**Важная оговорка о том, чего в веб-API нет.** В материалах про управление разрешениями иногда встречаются свойства и методы вроде `isPermanentlyDenied` или `openAppSettings()` — но это не часть веб-стандарта. Эти конкретные имена происходят из **мобильной** разработки (например, из пакета `permission_handler` для Flutter, где Android/iOS действительно различают «обычный» отказ и отказ с пометкой «больше не спрашивать»). Веб-спецификация Permissions API устроена проще: у `PermissionStatus` есть только сами три состояния выше, без встроенного различения «временного» и «постоянного» `denied`, и без API для программного открытия настроек браузера — на вебе браузер сам решает, когда снова показывать диалог, а разработчик может лишь наблюдать за состоянием через событие `change` и текстом на странице объяснять пользователю, как включить разрешение вручную через интерфейс браузера (у каждого браузера этот путь свой, и заранее сослаться на него программно нельзя).

### 1.2. Основные типы разрешений в 2026 году

Современные браузеры поддерживают широкий спектр разрешений, доступных через `navigator.permissions.query({ name: '...' })`. Состав поддерживаемых имён отличается между браузерами — некоторые из перечисленных ниже (например, `clipboard-read`, `clipboard-write`) реализованы только в части движков, поэтому перед использованием стоит проверять конкретное имя через `try/catch`, а не считать список универсальным:

| Тип разрешения | Описание |
|----------------|----------|
| **`camera`** | Доступ к камере устройства |
| **`microphone`** | Доступ к микрофону |
| **`geolocation`** | Доступ к геолокации |
| **`notifications`** | Показ push-уведомлений |
| **`clipboard-read`** | Чтение буфера обмена |
| **`clipboard-write`** | Запись в буфер обмена |
| **`storage-access`** | Доступ к хранилищу в сторонних контекстах |

### 1.3. Практическое использование Permissions API

**Проверка статуса разрешения:**

```javascript
// Проверка статуса разрешения на камеру
async function checkCameraPermission() {
    const status = await navigator.permissions.query({ name: 'camera' });
    
    console.log(`Статус: ${status.state}`); // 'granted', 'denied', 'prompt'
    
    // Отслеживание изменений статуса
    status.addEventListener('change', () => {
        console.log(`Статус изменился: ${status.state}`);
        // Адаптация UI в зависимости от нового статуса
    });
    
    return status;
}
```

**Запрос разрешения на множественные функции:**

```javascript
// Запрос разрешений на камеру и микрофон
async function requestMediaPermissions() {
    try {
        // Запрос через MediaDevices API автоматически триггерит запрос разрешений
        const stream = await navigator.mediaDevices.getUserMedia({
            video: true,
            audio: true
        });
        
        // После получения доступа проверяем статус
        const cameraStatus = await navigator.permissions.query({ name: 'camera' });
        const micStatus = await navigator.permissions.query({ name: 'microphone' });
        
        return {
            camera: cameraStatus.state === 'granted',
            microphone: micStatus.state === 'granted'
        };
    } catch (error) {
        console.error('Доступ к медиа-устройствам отклонен:', error);
        return { camera: false, microphone: false };
    }
}
```

### 1.4. Обработка отказа в разрешении

Если пользователь отклонил разрешение, приложение должно корректно обработать эту ситуацию — но, в отличие от мобильных приложений, веб-платформа не даёт программного способа узнать, является ли отказ «постоянным», и не даёт API для прямого перехода в настройки:

```javascript
async function handlePermissionRequest() {
    const status = await navigator.permissions.query({ name: 'geolocation' });
    
    if (status.state === 'denied') {
        // Веб-API не различает "временный" и "постоянный" отказ —
        // показываем универсальную инструкцию для пользователя
        showMessage(
            'Доступ к геолокации отклонён. Чтобы включить его, откройте настройки ' +
            'сайта через иконку рядом с адресной строкой браузера.'
        );
        // Прямой программный переход в настройки браузера веб-платформа не предоставляет —
        // это осознанное ограничение безопасности, а не недостающая фича
    } else if (status.state === 'prompt') {
        // Можно запросить разрешение — например, через сам API, использующий это разрешение
        showMessage('Разрешение на геолокацию необходимо для работы приложения.');
    }
}
```

### 1.5. Группы разрешений

Некоторые связанные разрешения (например, `camera` и `microphone` при вызове `getUserMedia({ video: true, audio: true })`) запрашиваются через единый системный диалог браузера — но это поведение конкретной реализации браузера, а не отдельный формализованный механизм «группировки» в самой спецификации Permissions API.

## 2. Private State Tokens: борьба с фродом без кук (Chrome-only)

Private State Tokens (до 2022 года называвшиеся Trust Tokens — переименованы именно из-за путаницы, которую создавало слово «trust») — это API, который позволяет сайтам передавать ограниченные приватные сигналы о доверии к пользователю между разными контекстами без использования идентифицирующих файлов cookie. Важная оговорка сразу: это **Chrome-специфичный API** в рамках программы Privacy Sandbox, а не общий веб-стандарт — Firefox и Safari его не реализуют. Из всей программы Privacy Sandbox это один из немногих API, которые Google продолжает поддерживать, тогда как большинство остальных уже депрекейтнуты.

### 2.1. Мотивация

Веб-экосистема сильно зависит от сигналов доверия для обнаружения мошеннических и спам-действий. Традиционно это делалось через отслеживание активности браузера с использованием стабильных идентификаторов. Private State Tokens решают эту проблему, предоставляя механизм, который позволяет сегментировать пользователей на "доверенных" и "недоверенных" без создания глобального идентификатора пользователя.

**Ключевое свойство:** Токены не персонализированы и не могут быть использованы для отслеживания пользователей. Они криптографически подписаны, что предотвращает их подделку.

### 2.2. Архитектура Private State Tokens

API работает на основе протокола Privacy Pass и использует три основные операции:

**1. Issuance (Выпуск токенов).** Когда origin доверяет пользователю (например, после успешного входа или прохождения капчи), он может выпустить пакет токенов:

```javascript
fetch('https://issuer.example/issue', {
    privateToken: {
        version: 1,
        operation: 'token-request'
    }
});
```

Браузер генерирует набор nonce (случайных чисел), "ослепляет" их (blinding — криптографическая техника, скрывающая данные) и отправляет на сервер. Сервер подписывает их и возвращает. Браузер "снимает ослепление" и сохраняет пары (nonce + подпись). **Сырые токены никогда не доступны JavaScript** — они хранятся и управляются исключительно браузером.

**2. Redemption (Погашение токенов).** Когда пользователь посещает другой сайт, этот сайт может запросить погашение токенов:

```javascript
// Проверка наличия токенов
const hasToken = await document.hasPrivateToken('https://issuer.example');

if (hasToken) {
    fetch('https://issuer.example/redeem', {
        privateToken: {
            version: 1,
            operation: 'token-redemption',
            refreshPolicy: 'none' // или 'refresh'
        }
    });
}
```

Если токены есть, браузер использует протокол Privacy Pass для погашения токена. Сервер проверяет подпись и может вернуть **Redemption Record (RR)** — запись о погашении, которая кешируется браузером.

**3. Forwarding Redemption Attestation (Пересылка аттестации).** RR могут быть переданы третьим сторонам через Fetch API:

```javascript
fetch('https://publisher.example/api', {
    privateToken: {
        version: 1,
        operation: 'send-redemption-record',
        issuers: ['https://issuer.example']
    }
});
```

RR добавляются в HTTP-заголовок `Sec-Redemption-Record`. Заголовок HTTP-only, доступ к RR через JavaScript невозможен напрямую.

### 2.3. Криптографические гарантии приватности

**Свойство Unlinkability (Невозможность связывания)** — ключевая гарантия приватности:

- Выпуск токенов **не может быть связан** с их погашением.
- Эмитент не может коррелировать выпуск токенов на одном сайте с их погашением на другом.
- Эмитент узнает только агрегированную информацию о том, какие сайты посещают пользователи, но не может связать это с конкретной личностью.

**Технические меры для защиты свойства Unlinkability:**

- **Key Consistency.** Сервер не может использовать разные приватные ключи для разных клиентов, что предотвратило бы деанонимизацию. Протокол требует публикации списка публичных ключей (не более 3 ключей) и верификации консистентности.
- **Защита от fingerprinting.** API не раскрывает новой информации, которую злоумышленники не могли бы получить через другие механизмы (например, через сетевые запросы).

### 2.4. Ограничения и лимиты

Чтобы предотвратить злоупотребления и утечку идентификационной информации, API имеет строгие ограничения:

- **Per-Site Issuer Limits.** Количество эмитентов токенов на один top-level origin жестко ограничено (например, не более 2). Это предотвращает использование большого количества эмитентов для создания канала передачи идентификационной информации.
- **Rate Limiting на Redemption.** Эмитенты могут ограничивать частоту погашения токенов, возвращая кешированные RR (Redemption Records) при слишком частых попытках.
- **Lifetime RR.** Время жизни RR ограничено либо через заголовок `Sec-Private-State-Token-Lifetime`, либо привязано к времени жизни ключа верификации.

Поскольку API работает только в Chrome, любая архитектура, полагающаяся на Private State Tokens как на единственный механизм борьбы с фродом, оставит пользователей Firefox и Safari без этой защиты — стоит проектировать её как одну из нескольких линий обороны, а не как единственную.

## 3. Federated Credential Management (FedCM): вход без сторонних кук — практически только в Chromium

Federated Credential Management API (FedCM) — это стандарт, разрабатываемый W3C и предоставляющий механизм для федеративной аутентификации (например, "Войти через Google") без использования сторонних cookies и навигационных редиректов. Прежде чем разбирать архитектуру, важно обозначить реальный статус кросс-браузерной поддержки на 2026 год, потому что он критически влияет на архитектурные решения: **Safari официально не реализует FedCM** — команда WebKit закрывает связанные запросы позиции формулировкой «Safari is not implementing FedCM in general». **Firefox приостановил разработку в августе 2025 года**: часть смежной инфраструктуры (Login Status API) поддерживается за флагом, но полноценной реализации FedCM нет, и сроков возобновления работы публично не называлось. Полная, стабильная поддержка есть только в Chrome (с версии 136), Edge и части Chromium-производных браузеров (Samsung Internet, Opera). Это делает FedCM де-факто Chromium-технологией, а не универсальным браузерным стандартом — на неё нельзя полагаться как на единственный механизм входа.

### 3.1. Проблема традиционной федеративной аутентификации

Традиционные механизмы федеративной аутентификации полагаются на **iframes, редиректы и сторонние cookies**. Это создает проблемы:

- **Приватность.** Браузеры не могут отличить легитимные сервисы идентификации от нежелательного отслеживания. Третьи стороны могут использовать эти механизмы для отслеживания пользователей по всей сети.
- **Ограничение сторонних cookies.** Современные браузеры ограничивают использование сторонних cookies, что ломает традиционные федеративные потоки.
- **Неконсистентный UX.** Сайты отображают большое количество кнопок входа (NASCAR problem), что загромождает интерфейс.

### 3.2. Как работает FedCM (в браузерах, где он реализован)

FedCM предоставляет **браузерно-опосредованный UI** для выбора аккаунта и входа. Вместо того чтобы сайт отображал кнопки входа, браузер показывает стандартизированный диалог выбора аккаунта.

**Два режима UI:**

- **Пассивный (Passive) режим.** Диалог появляется автоматически при загрузке страницы, если пользователь уже вошел в систему у Identity Provider (IdP).
- **Активный (Active) режим.** Диалог появляется только после действия пользователя (например, клика по кнопке "Войти").

**Базовый код входа через FedCM — обязательно с проверкой доступности и fallback:**

```javascript
async function signInWithFedCM() {
    // FedCM недоступен в Safari и практически недоступен в Firefox —
    // всегда нужен альтернативный путь входа
    if (!('IdentityCredential' in window)) {
        return signInWithFallbackMethod(); // например, классический OAuth-редирект
    }

    try {
        const credential = await navigator.credentials.get({
            identity: {
                providers: [{
                    configURL: 'https://accounts.idp.example/config.json',
                    clientId: 'rp-client-id',
                    nonce: 'some-random-nonce'
                }]
            }
        });
        
        // credential содержит информацию о выбранном аккаунте
        console.log('Авторизация успешна:', credential);
        
        // Отправка токена на сервер RP
        await sendTokenToServer(credential);
    } catch (error) {
        if (error.name === 'AbortError') {
            console.log('Пользователь отменил вход');
        } else {
            console.error('Ошибка входа:', error);
            return signInWithFallbackMethod();
        }
    }
}
```

### 3.3. Преимущества FedCM (там, где он работает)

**Поддержка без сторонних cookies.** FedCM работает даже в режиме инкогнито и когда сторонние cookies отключены — в браузерах, где он реализован. Он интегрирован с другими Privacy Sandbox API — например, Storage Access API использует FedCM как сигнал доверия.

**Улучшенный UX.** Вместо множества кнопок входа FedCM показывает браузерный диалог с аккаунтами, отфильтрованными по релевантности: сначала показываются аккаунты, недавно использовавшиеся на устройстве, затем аккаунты, уже использовавшиеся на RP, и только потом новые аккаунты.

**Безопасность.** FedCM снижает поверхность для фишинга, так как пользователь использует управляемые IdP аккаунты вместо создания новых паролей для каждого сайта.

**Поддержка множественных IdP.** FedCM позволяет сайту поддерживать несколько Identity Providers без загромождения UI — там, где браузер поддерживает сам API.

### 3.4. Сравнение: Традиционный вход vs FedCM

| Аспект | Традиционный вход | FedCM |
|--------|------------------|-------|
| **Поддержка браузеров** | Универсальная | Только Chromium (Chrome 136+, Edge, Samsung Internet, Opera). Safari официально отказалась, Firefox приостановил разработку |
| **Сторонние cookies** | Требуются | Не требуются (в браузерах с поддержкой) |
| **UI** | Управляется RP (кнопки) | Браузерный диалог |
| **Работа в инкогнито** | Может не работать | Работает (в браузерах с поддержкой) |
| **Обязательность fallback** | Нет | Да — без fallback пользователи Safari и Firefox не смогут войти |

### 3.5. Кто должен использовать FedCM — и с какой оговоркой

FedCM может быть полезен для:
- **Identity Providers (IdP),** которые хотят предложить бескукенную аутентификацию клиентам на Chromium — с обязательным сохранением классического потока для остальных браузеров.
- **Relying Parties (RP)** с множеством IdP-интеграций, которые хотят улучшить опыт для доли пользователей на Chromium, не отказываясь от универсального fallback.

Учитывая, что Safari категорически не планирует поддержку, а Firefox — на неопределённой паузе, ни один продакшн-проект в 2026 году не может использовать FedCM как единственный механизм входа. Это дополнение к существующим методам аутентификации, а не их замена.

## Итог

Модель изоляции и разрешений браузера 2026 года — это трёхкомпонентная система с очень разной зрелостью составляющих:

- **Permissions API** — зрелая, кросс-браузерная технология (Baseline с сентября 2022 года). Поддерживает три состояния (`granted`, `denied`, `prompt`) и позволяет отслеживать изменения статуса. Важно не путать веб-API со свойствами и методами мобильных SDK вроде Flutter (`isPermanentlyDenied`, `openAppSettings()`) — на вебе их не существует.
- **Private State Tokens** (ранее Trust Tokens) — криптографический механизм для борьбы с фродом без использования идентифицирующих файлов cookie, основанный на протоколе Privacy Pass. Реализован **только в Chrome**, поэтому не может быть единственной линией защиты от фрода.
- **Federated Credential Management (FedCM)** — стандарт для федеративной аутентификации без сторонних cookies. Технически интересен, но по факту доступен **только в Chromium-браузерах**: Safari официально отказалась от реализации, Firefox приостановил работу в августе 2025 года. Любое использование FedCM в продакшне требует полноценного fallback на классическую аутентификацию.
