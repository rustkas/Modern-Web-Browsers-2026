# Глава 3. Рендеринг и композитинг без компромиссов

В 2026 году рендеринг перестал быть просто процессом отрисовки пикселей на экране. Теперь это интеллектуальный конвейер, который работает как высокопроизводительная графическая подсистема внутри браузерной мета-ОС. Современные движки, такие как Blink (Chromium), Gecko (Firefox) и WebKit (Safari), научились балансировать между визуальной сложностью интерфейса и жесткими требованиями к энергоэффективности, обеспечивая 120 FPS на современных дисплеях при минимальном потреблении батареи.

Эта глава детально разбирает полный пайплайн рендеринга 2026 года: от парсинга HTML и CSS до финального композитинга на GPU. Рассматриваются современные Layout Engine (Flexbox 2026, Grid 3.0, Masonry/Grid Lanes), а также механизмы Offscreen Rendering и энергосбережения, которые позволяют браузеру оставаться эффективным даже на мобильных устройствах с ограниченным запасом батареи. Как и в предыдущих главах, часть рассматриваемых возможностей всё ещё находится в стадии внедрения в разных движках — это отмечено по ходу изложения.

## 1. Пайплайн рендеринга: от DOM-дерева до экранных пикселей

Процесс превращения текстового кода в интерактивное изображение в 2026 году следует строгому многоэтапному конвейеру (rendering pipeline), где каждый шаг оптимизирован для максимальной производительности. Полный пайплайн состоит из пяти основных этапов, но в зависимости от выполняемого действия браузер может пропускать некоторые из них для экономии ресурсов.

### 1.1. Этап 1: Загрузка и парсинг

**HTML-парсинг.** Браузер загружает HTML-код по сети (или из кеша) и преобразует его в **DOM-дерево** (Document Object Model). Парсинг HTML выполняется последовательно, но современные браузеры используют **предварительный сканер (preload scanner)**, который, не дожидаясь завершения парсинга, анализирует HTML на предмет внешних ресурсов (скриптов, стилей, изображений) и запускает их загрузку параллельно.

**CSS-парсинг.** Одновременно с HTML парсится CSS (из внешних файлов, тегов `<style>` или инлайновых стилей) и строится **CSSOM** (CSS Object Model). CSSOM представляет собой дерево стилей, где каждый узел содержит вычисленные значения свойств с учетом каскада, специфичности и наследования.

**Блокирующий рендеринг (Render-Blocking).** По умолчанию CSS является блокирующим ресурсом: браузер не начнет строить **Render Tree** (дерево рендеринга) до тех пор, пока не будет загружен и распарсен весь CSS. Это гарантирует, что страница не отобразится "без стилей" (FOUC — Flash of Unstyled Content). Однако в 2026 году разработчики могут использовать атрибут `media` в `<link>` для указания, что определенные стили применяются только для определенных условий (например, `media="print"`), и они не блокируют рендеринг.

### 1.2. Этап 2: Построение Render Tree

После того как DOM и CSSOM построены, браузер объединяет их в **Render Tree** (дерево рендеринга). Render Tree содержит только те элементы, которые будут видны на экране. Элементы с `display: none` (но не `visibility: hidden`) исключаются из Render Tree. Каждый узел Render Tree содержит информацию о геометрии, стилях и визуальных свойствах элемента.

Важное отличие от DOM: Render Tree — это отдельная структура, не идентичная DOM. Она оптимизирована для быстрого вычисления макета и отрисовки.

### 1.3. Этап 3: Layout (Макет / Reflow)

На этапе Layout браузер вычисляет точную геометрию (координаты, ширину, высоту, отступы, границы) каждого узла в Render Tree. Этот процесс также называется **Reflow** (перекомпоновка). Layout выполняется относительно корневого элемента (обычно `<html>`) и учитывает все CSS-свойства, влияющие на размеры и позиционирование: `width`, `height`, `padding`, `margin`, `border`, `position`, `float`, `flex`, `grid` и другие.

**Особенности Layout в 2026 году:**

- **Изоляция изменений (Layout Containment).** С помощью CSS-свойства `contain: layout` разработчик может указать, что изменения внутри элемента не влияют на элементы снаружи. Это позволяет браузеру пересчитывать макет только внутри контейнера, а не на всей странице.
- **Инкрементальный Layout.** Движки рендеринга выполняют макет не за один проход, а инкрементально: при изменении DOM или CSS браузер пересчитывает только те части дерева, которые затронуты изменениями. Благодаря этому сложные страницы (например, с тысячами элементов) остаются отзывчивыми.
- **Асинхронный Layout.** В некоторых сценариях (например, при загрузке шрифтов или изображений) браузер может выполнять layout асинхронно, не блокируя основной поток.

**Стоимость Layout.** Этап Layout — один из самых ресурсоемких в пайплайне рендеринга. Он может занимать десятки миллисекунд на сложных страницах. Для минимизации Layout разработчикам рекомендуется:

- Избегать частого чтения свойств, которые триггерят Reflow (`offsetTop`, `scrollHeight`, `getComputedStyle` в циклах).
- Использовать `transform` и `opacity` для анимаций — они не вызывают Layout и Paint, только Compositing.
- Применять `will-change: transform, opacity` для элементов, которые будут анимироваться, чтобы браузер создал отдельный слой композитинга.

### 1.4. Этап 4: Paint (Отрисовка / Рекординг)

После вычисления макета браузер переходит к этапу Paint. Здесь он определяет, **как** будут выглядеть элементы: цвета, фоны, тени, градиенты, текст, изображения, рамки, скругления углов и другие визуальные свойства.

На этом этапе браузер генерирует **списки команд рисования (paint records)** для графического движка (например, Skia в Chromium). Эти команды содержат инструкции типа: "нарисовать прямоугольник размером X на Y с цветом #FF0000 в позиции (10, 20)".

**Особенности Paint в 2026 году:**

- **Layer-based Painting.** Браузер разбивает страницу на слои (layers) и рисует каждый слой отдельно. Слои создаются для элементов с `will-change`, `transform: translateZ(0)` (или любой другой 3D-трансформацией), `opacity < 1`, видео, canvas и других.
- **Tile-based Painting.** Каждый слой разбивается на квадратные тайлы (обычно 256x256 или 512x512 пикселей). Это позволяет браузеру рисовать только те тайлы, которые видны пользователю, и экономить память.
- **Асинхронный Paint.** Рисование тайлов может выполняться в отдельных потоках (Worker Threads), не блокируя основной поток.

**Стоимость Paint.** Paint — также дорогостоящая операция, особенно при использовании сложных теней, фильтров, градиентов и закруглений. Для минимизации Paint:

- Используйте простые цвета вместо градиентов и сложных фонов.
- Ограничьте количество слоев (слишком много слоев увеличивает использование памяти GPU).
- Используйте `contain: layout style paint` для изоляции изменений стилей и предотвращения перерисовки соседних элементов.

### 1.5. Этап 5: Composite (Композитинг)

Финальный этап пайплайна — **композитинг**. На этом этапе браузер берет все ранее подготовленные растровые тайлы (пиксельные карты) из разных слоев, накладывает их друг на друга с учетом прозрачности, трансформаций и эффектов, и выводит финальное изображение на экран.

Композитинг выполняется исключительно на **GPU** (Graphics Processing Unit), что делает его очень быстрым. Браузер отправляет команды на GPU через графические API: Vulkan, Metal или Direct3D 12 (в зависимости от ОС).

**Что происходит во время композитинга:**

- **Позиционирование слоев.** Каждый слой имеет координаты (x, y, z) относительно окна просмотра.
- **Применение трансформаций.** К слоям применяются CSS-трансформации (`translate`, `scale`, `rotate`, `skew`), которые выполняются аппаратно на GPU без участия основного потока.
- **Наложение (Blending).** Слои с прозрачностью (`opacity < 1`) или эффектами смешивания (`mix-blend-mode`) накладываются друг на друга.
- **Отсечение (Clipping).** Области, выходящие за границы окна просмотра или родительского элемента, обрезаются.
- **Вывод на экран.** Финальный кадр передается на дисплей через системный видеодрайвер.

**Особенности композитинга в 2026 году:**

- **Мульти-экранная поддержка.** Браузер поддерживает работу с несколькими мониторами с разными частотами обновления (например, 60 Гц и 120 Гц), синхронизируя композитинг для каждого дисплея отдельно.
- **Аппаратное ускорение видеопотоков.** Видео и WebRTC-потоки рендерятся как отдельные слои с поддержкой HDR и широкого цветового охвата (WCG).
- **Переменная частота кадров (VRR — Variable Refresh Rate).** В 2026 году браузеры поддерживают адаптивную частоту обновления (G-Sync, FreeSync), что снижает энергопотребление при просмотре статичного контента.

**Почему Compositing самый быстрый этап:**

- Операции выполняются на GPU, а не на CPU.
- Не требует пересчета Layout или Paint.
- Может выполняться синхронно с частотой обновления экрана (60 Гц, 120 Гц или выше).

## 2. Новый Layout Engine: Flexbox 2026, Grid 3.0 и Masonry / Grid Lanes

К 2026 году возможности CSS-верстки значительно расширились за счет новых стандартов. Здесь стоит сразу оговориться: зрелость этих стандартов сильно различается — от полностью стабильных (Flexbox-улучшения) до всё ещё экспериментальных (Masonry/Grid Lanes, `if()`) — и книга указывает актуальный статус для каждого.

### 2.1. Flexbox 2026

**Flexbox (Flexible Box Layout)** — стандарт для создания одномерных раскладок (в строку или в столбец). В 2026 году Flexbox получил несколько улучшений:

- **`gap` для Flexbox.** Ранее `gap` работал только в Grid. Теперь `row-gap` и `column-gap` полностью поддерживаются во Flexbox, что упрощает управление промежутками между элементами без использования маргинов.
- **`align-items: stretch` с учетом контента.** Улучшенная обработка растяжения элементов с учетом максимального размера содержимого.
- **`flex-wrap: wrap` и выравнивание.** Улучшена обработка многорядных флекс-контейнеров, особенно с `align-content` и распределением свободного пространства.

Это одна из самых зрелых частей главы — `gap` во Flexbox и связанные улучшения давно достигли статуса Baseline и одинаково работают во всех трёх движках.

**Пример использования Flexbox 2026:**

```css
.container {
  display: flex;
  flex-wrap: wrap;
  gap: 20px 30px; /* row-gap 20px, column-gap 30px */
  align-content: center;
}
```

### 2.2. Grid 3.0 (Subgrid)

**CSS Grid** стал стандартом для двумерных раскладок. Наиболее зрелое дополнение Grid Level 3 к 2026 году — это Subgrid:

- **Subgrid (подсетка).** Позволяет дочернему элементу наследовать грид-линии родительского контейнера. Это упрощает создание сложных, выровненных по вертикали макетов без дублирования определений треков. Subgrid — Baseline-функциональность, поддерживается во всех современных версиях трёх движков.

```css
.parent {
  display: grid;
  grid-template-columns: 1fr 2fr 1fr;
}

.child {
  display: grid;
  grid-template-columns: subgrid; /* наследует 1fr 2fr 1fr от родителя */
}
```

### 2.3. Masonry Layout / Grid Lanes (нативная кирпичная раскладка)

**Masonry Layout** — долгожданная нативная поддержка «кирпичной» раскладки (как в Pinterest или Unsplash), где элементы разной высоты выстраиваются в несколько колонок, минимизируя вертикальные промежутки. Раньше для реализации Masonry требовались тяжелые JavaScript-библиотеки (например, Masonry.js) или сложные вычисления с позиционированием.

Здесь важно внести ясность в терминологию, потому что путь этой технологии к стандарту был извилистым. За несколько лет конкурировали три разных синтаксиса: `grid-template-rows: masonry` (изначально предложен Firefox и Safari), `display: masonry` (прототип Chrome) и `item-flow` (альтернативное предложение WebKit). CSS Working Group в итоге остановилась на едином имени — **`display: grid-lanes`** (и `inline-grid-lanes` для горизонтального варианта), и именно эта запись зафиксирована в текущей документации MDN как финальный вариант спецификации CSS Grid Level 3. Это не отдельная технология наряду с masonry — это его актуальное официальное название.

**Статус поддержки в браузерах на 2026 год:**

- **Safari** — первой реализовала стабильную версию (Safari 26.4+).
- **Chrome и Firefox** — реализация доступна за экспериментальными флагами, стабильный релиз ожидается позже в течение 2026 года.

Полностью интероперабельной, не требующей флагов поддержки во всех трёх движках одновременно на момент написания книги ещё нет — при использовании в продакшне обязательно оборачивайте код в `@supports`, чтобы браузеры без поддержки корректно откатывались на обычный Grid.

```css
.masonry-container {
  display: grid-lanes;
  grid-template-columns: repeat(3, 1fr);
  gap: 20px;
}

.item {
  /* элементы автоматически размещаются в дорожке с наибольшим доступным местом */
}

/* Прогрессивное улучшение с откатом на обычный Grid */
@supports not (display: grid-lanes) {
  .masonry-container {
    display: grid;
    grid-template-columns: repeat(3, 1fr);
    gap: 20px;
  }
}
```

**Преимущества нативного Masonry / Grid Lanes:**

- Высокая производительность (расчет выполняется на уровне Layout Engine, без участия JavaScript).
- В отличие от старого «колоночного» хака (`columns: 3`), сохраняется порядок DOM, что важно для доступности и навигации с клавиатуры.
- Интеграция с другими CSS-свойствами: `gap`, `align-items`, `justify-items`.

### 2.4. CSS `if()` — условные выражения в значениях свойств (пока не Baseline)

В 2026 году CSS начал получать поддержку условных выражений через функцию `if()`, позволяющую браузеру принимать решения о значении свойства прямо в CSSOM, без JavaScript и дублирования блоков `@media`/`@container`. Важная оговорка сразу: по данным MDN, `if()` помечен как экспериментальный и **не имеет статуса Baseline** — на 2026 год он реализован только в Chrome и Edge (начиная с версии 137), тогда как в Firefox поддержка ещё разрабатывается, а в Safari стоит в дорожной карте на 2026–2027 годы.

Важна и точность синтаксиса: `if()` не принимает произвольные булевы сравнения переменных — условиями внутри него служат `media()`, `style()` (для container style queries) или `supports()` запросы:

```css
.card {
  padding: if(media(width >= 768px): 1.5rem; else: 1rem);
  border-radius: if(supports(corner-shape: squircle): 12px; else: 8px);
}
```

Пока `if()` не станет Baseline, для продакшн-кода стоит использовать его как прогрессивное улучшение поверх безопасного значения по умолчанию, а не как основной механизм:

```css
/* Безопасное значение по умолчанию для всех браузеров */
.card {
  padding: 1rem;
}

/* Улучшение для браузеров с поддержкой if() */
@supports (padding: if(media(width >= 768px): 1.5rem; else: 1rem)) {
  .card {
    padding: if(media(width >= 768px): 1.5rem; else: 1rem);
  }
}
```

### 2.5. View Transitions (переходы между состояниями и документами)

**View Transitions API** (ранее известный как Shared Element Transitions) позволяет создавать бесшовные анимационные переходы между состояниями одной страницы. Здесь важно различать две части технологии по зрелости: переходы **внутри одного документа** (same-document, типичный сценарий для SPA) достигли статуса Baseline и одинаково работают во всех современных браузерах. А вот **кросс-документные переходы** (для многостраничных MPA-приложений, когда переход происходит между полноценными навигациями) на 2026 год всё ещё **не реализованы в Firefox** — то есть этой частью API пока стоит пользоваться как прогрессивным улучшением, а не рассчитывать на неё как на универсальный механизм.

Как это работает (принцип одинаков для обоих сценариев):

1. Браузер захватывает «старое» состояние страницы (скриншот).
2. Выполняется переход на новую страницу или в новое состояние.
3. Браузер захватывает «новое» состояние.
4. Выполняется морфинг (плавное преобразование) между старым и новым состояниями.

```css
/* CSS для управления View Transitions */
::view-transition-old(root) {
  animation: fade-out 0.3s ease-in;
}

::view-transition-new(root) {
  animation: fade-in 0.3s ease-out;
}
```

```javascript
// Запуск same-document перехода — Baseline, работает везде
document.startViewTransition(() => {
  // Обновление DOM или навигация
  navigateToNewPage();
});
```

Same-document View Transitions делают SPA визуально неотличимыми от нативных мобильных приложений, повышая воспринимаемую производительность. Для MPA-сценариев (кросс-документные переходы) закладывайте фолбэк без анимации для Firefox.

## 3. Offscreen Rendering и энергосбережение

Браузер как мета-ОС берет на себя управление ресурсами устройства для продления времени автономной работы. Оптимизация рендеринга в 2026 году включает методы энергосбережения, которые снижают потребление батареи без потери производительности. Этот раздел книги требует особенно внимательного чтения статусов поддержки: часть API здесь либо экспериментальна и Chromium-специфична, либо вовсе была выведена из части браузеров по соображениям приватности.

### 3.1. Деприоритизация закадрового контента

Браузер автоматически снижает частоту обновления и выделяемые ресурсы для элементов, которые находятся вне области видимости (**Offscreen content**). Это реализуется через:

- **Снижение FPS для Offscreen-вкладок.** Если вкладка неактивна (находится на заднем плане), браузер ограничивает частоту обновления до 1–2 кадров в секунду.
- **Приостановка анимаций.** CSS-анимации и JavaScript-анимации (`requestAnimationFrame`) замедляются или полностью останавливаются для элементов вне экрана.
- **Отложенный рендеринг тайлов.** Тайлы, которые не видны пользователю (вне скролла), не растеризуются, пока не приблизятся к области просмотра.

```javascript
// API для проверки видимости элемента
const isVisible = element.checkVisibility({
  checkOpacity: true,
  checkVisibilityCSS: true,
});
```

### 3.2. Пропуск этапов конвейера (Pipeline Skipping)

Если пользователь совершает простое действие (например, скроллит страницу), Blink может пропускать этапы Layout и Paint, обновляя положение слоев сразу в композиторе.

- **Скролл.** При скролле браузер перемещает существующие слои, не пересчитывая Layout и не перерисовывая Paint. Это выполняется на GPU и практически не нагружает основной поток.
- **Трансформации.** Анимации с использованием `transform` и `opacity` выполняются только на этапе Composite, пропуская Layout и Paint. Это делает их самыми производительными для анимации.
- **Изменение цвета или фона.** Такие изменения требуют только Paint (но не Layout), что дешевле полного Reflow.

### 3.3. Умная ленивая загрузка (Lazy Loading 2026)

Нативная поддержка ленивой загрузки (через атрибуты `loading="lazy"`) теперь распространяется не только на изображения, но и на видео, аудио и iframes.

```html
<img src="large-image.jpg" loading="lazy" decoding="async" />
<video src="movie.mp4" loading="lazy"></video>
<iframe src="map.html" loading="lazy"></iframe>
```

Что происходит под капотом:

- Браузер не загружает ресурс, пока он не приблизится к области просмотра (viewport) на определенное расстояние (расстояние предварительной загрузки, обычно 200–300 пикселей).
- Для изображений и видео браузер также откладывает декодирование до момента появления на экране.
- Это предотвращает лишние сетевые запросы, экономит трафик и снижает нагрузку на CPU/GPU.

### 3.4. Compute Pressure API и адаптивный рендеринг (экспериментальный, Chromium-only)

**Compute Pressure API** позволяет странице отслеживать нагрузку на CPU в реальном времени через дискретные состояния давления (`nominal`, `fair`, `serious`, `critical`) — это полезно, например, для видеоконференций, которым нужно снижать качество потока при перегрузке системы. Важно точно понимать возможности API и его статус:

- **Что API реально измеряет.** Только давление на CPU. Он не сообщает температуру устройства и не даёт доступа к уровню заряда батареи напрямую — это часто встречающееся заблуждение, которое стоит сразу развеять.
- **Статус поддержки.** API не имеет статуса Baseline и по состоянию на 2026 год реализован только в Chromium-браузерах; в Firefox и Safari он не поддерживается.

```javascript
// Отслеживание нагрузки на CPU (Chromium-only)
if ('PressureObserver' in window) {
  const observer = new PressureObserver((records) => {
    for (const record of records) {
      if (record.state === 'critical') {
        // Система перегружена — упрощаем интерфейс
        simplifyVisualEffects();
      }
    }
  });
  observer.observe('cpu');
}
```

### 3.5. Battery-Aware поведение: реальность гораздо скромнее, чем может показаться

Раньше в подобных книгах можно было встретить раздел про повсеместное «battery-aware rendering» на основе Battery Status API. К 2026 году это направление стоит описывать точнее, потому что реальная картина сильно отличается от идеи «браузер всегда знает заряд батареи и подстраивается под него»:

- **Firefox удалил Battery Status API ещё в версии 52 (2017 год)** после того, как исследования показали, что комбинация уровня заряда и времени до разрядки создаёт достаточно уникальный отпечаток для фингерпринтинга пользователя.
- **Safari/WebKit никогда не реализовывал этот API** — по тем же соображениям приватности.
- **В Chrome/Chromium API технически всё ещё доступен**, но со значительными ограничениями: работает только в защищённом контексте (HTTPS), а точность отдаваемых значений намеренно снижена (уровень заряда округляется, время зарядки/разрядки округляется до 30 секунд), чтобы уменьшить его пригодность для фингерпринтинга.

Практический вывод для 2026 года: полагаться на `navigator.getBattery()` как на основной механизм адаптации интерфейса не стоит — это в лучшем случае необязательное улучшение только для Chromium-пользователей, с обязательной проверкой доступности API и понятной деградацией для Firefox и Safari, где метод просто не существует:

```javascript
if ('getBattery' in navigator) {
  navigator.getBattery().then((battery) => {
    if (battery.level < 0.2) {
      // Работает только в Chromium; Firefox и Safari сюда не попадут
      reduceVisualEffects();
    }
  });
}
```

Что действительно кросс-браузерно и заслуживает предпочтения в 2026 году — это связка **`prefers-reduced-motion`** (CSS media query, Baseline) для уважения пользовательских настроек анимации и упомянутого выше `checkVisibility()`/офскрин-деприоритизации, которые не зависят от доступа к состоянию батареи и работают во всех движках одинаково.

- **Dark Mode для экономии энергии.** На OLED-экранах тёмная тема действительно снижает энергопотребление (чёрные пиксели на OLED не потребляют энергию) — но это следствие физики самого дисплея, а не результат работы какого-то специального «battery-aware» API: браузеру достаточно уважать `prefers-color-scheme`, что он и делает кросс-браузерно.

## Итог

Современный пайплайн рендеринга в 2026 году — это сложный, многоэтапный процесс, где каждый этап (Layout, Paint, Composite) оптимизирован для максимальной производительности. Понимание этого конвейера критически важно для достижения Core Web Vitals: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1.

Новый Layout Engine поддерживает передовые стандарты CSS, но с разной степенью зрелости: Flexbox-улучшения и Subgrid — уже Baseline; Masonry-раскладка (в финальной спецификации — Grid Lanes, `display: grid-lanes`) и CSS `if()` — всё ещё экспериментальны и требуют progressive enhancement; View Transitions same-document — Baseline, а кросс-документные переходы пока не работают в Firefox.

Offscreen Rendering и часть механизмов энергосбережения (деприоритизация фоновых вкладок, ленивая загрузка) работают кросс-браузерно, но Compute Pressure API и в особенности Battery Status API — Chromium-специфичные, ограниченные по точности и не гарантированные технологии; полагаться на них как на основной механизм адаптации интерфейса не стоит.

В следующей главе мы перейдем к системным API для работы с данными и файловой системой: IndexedDB 3.0, OPFS (Origin Private File System) и File System Access API — и там тоже разберём, что из этого действительно кросс-браузерно, а что специфично для отдельных движков.
