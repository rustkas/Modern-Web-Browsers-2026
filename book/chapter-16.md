# Глава 16. Сборка и доставка кода в эпоху HTTP/3

В 2026 году доставка кода в браузер перестала быть просто "загрузкой файлов". Современные веб-приложения используют сложные стратегии: ES-модули с import maps для управления зависимостями, динамические импорты для кодового сплиттинга, предсказательные механизмы Speculation Rules API для упреждающей загрузки страниц и гибридные подходы к рендерингу, сочетающие SSR, CSR и другие режимы. Эта глава последовательно разбирает три ключевых аспекта: управление модулями через Import Maps и ES-модули; динамический импорт и спекулятивные загрузки на уровне браузера; и выбор между режимами рендеринга (SSR, CSR, SSG, ISR) в 2026 году.

---

## 1. ES-модули и Import Maps 2026

ES-модули стали стандартом де-факто для организации JavaScript-кода в браузере. В 2026 году экосистема модулей полностью зрелая: все современные браузеры поддерживают базовый синтаксис import/export, а Import Maps позволяют использовать "голые" спецификаторы (bare specifiers) без указания полных путей.

### 1.1. ES-модули в браузере 2026

Нативные ES-модули поддерживаются во всех актуальных версиях браузеров:

```html
<script type="module">
    import { render } from './app.js';
    render();
</script>
```

**Ключевые возможности ES-модулей 2026 года:**

- **`modulepreload`** — предзагрузка модулей до их выполнения. Поддерживается во всех браузерах с Chrome 66+, Firefox 115+, Safari 17.5+.
- **Top-Level Await** — использование `await` на верхнем уровне модулей. Доступен в Chrome 89+, Firefox 89+, Safari 15+.
- **Module Workers** — использование ES-модулей в Web Workers. Поддерживается во всех современных браузерах.
- **JSON и CSS Modules** — импорт JSON и CSS как модулей через синтаксис `with { type: '...' }` (Import Attributes). Здесь два разных статуса, которые важно не путать: **JSON Modules с 2025 года стали по-настоящему кросс-браузерными** — достигли статуса Baseline Newly Available в рамках проекта Interop 2025 и поддерживаются в Chrome 123+, **Firefox 128+** и Safari 17.2+. А вот **CSS Modules остаются Chromium-only** (Chrome/Edge 93+) — Firefox и Safari пока находятся в стадии разработки поддержки, конкретных сроков не называлось.

### 1.2. Import Maps: управление зависимостями

**Import Maps** — это механизм, позволяющий использовать "голые" спецификаторы (bare specifiers) в JavaScript-модулях. До появления import maps такой код:

```javascript
import { createElement } from 'react';
```

вызывал ошибку в браузерах с нативной поддержкой модулей, так как браузер не знал, куда указывает `'react'`.

**Import Map** определяет, как голые спецификаторы преобразуются в реальные URL:

```html
<script type="importmap">
{
    "imports": {
        "react": "https://cdn.jsdelivr.net/npm/react@19/index.js",
        "react-dom": "https://cdn.jsdelivr.net/npm/react-dom@19/index.js",
        "lodash": "/node_modules/lodash-es/lodash.js"
    },
    "scopes": {
        "/src/": {
            "react": "/src/vendor/react-custom.js"
        }
    },
    "integrity": {
        "/node_modules/lodash-es/lodash.js": "sha384-abc123..."
    }
}
</script>
```

**Поддержка Import Maps в 2026 году:**

| Браузер | Версия |
|---------|--------|
| Chrome | 89+ |
| Firefox | 108+ |
| Safari | 16.4+ |
| Edge | 89+ |

**Новые возможности Import Maps 2026 года:**

- **Multiple Import Maps.** Несколько import map могут существовать на одной странице (Chrome 135+).
- **Import Map Integrity.** Проверка целостности импортируемых ресурсов через поле `integrity` (Chrome 127+, Firefox 138+).
- **`import.meta.resolve`.** Стандартный метод для резолвинга URL относительно текущего модуля (Chrome 105+, Firefox 106+, Safari 16.4+).

**Полифиллы для старых браузеров:**

Для браузеров без поддержки import maps можно использовать `es-module-shims` — полифилл, который переписывает спецификаторы и загружает модули через Blob URL.

### 1.3. Практические рекомендации

В 2026 году рекомендуется использовать **Import Maps всегда**, даже если вы не используете голые спецификаторы. Это делает код более чистым и переносимым между средами. Важно: import map должен быть определен до первого `<script type="module">` на странице.

## 2. Динамический import и Code Splitting

Динамический импорт (`import()`) — это стандартный механизм для ленивой загрузки кода в браузере. Он позволяет загружать модули только тогда, когда они действительно нужны, что сокращает начальный размер бандла и ускоряет загрузку страницы.

### 2.1. Динамический импорт

Синтаксис динамического импорта:

```javascript
// Базовый импорт
import('/some-module.js')
    .then((module) => {
        // Использование модуля
        module.default();
    })
    .catch((error) => {
        console.error('Ошибка загрузки модуля:', error);
    });

// С использованием async/await
async function loadComponent() {
    const { default: Component } = await import('./Component.js');
    return Component;
}
```

**Когда использовать динамический импорт:**

- Для компонентов, которые появляются только при определенных действиях пользователя (модальные окна, сложные формы).
- Для страниц в SPA-маршрутизации (lazy loading).
- Для тяжелых библиотек (графики, обработка данных), которые нужны не на каждой странице.

### 2.2. React.lazy и Suspense

В React динамические импорты интегрируются через `React.lazy` и `Suspense`:

```javascript
import { lazy, Suspense } from 'react';

const SmileyFace = lazy(() => import('./smiley-face.tsx'));

function App() {
    return (
        <div>
            <Suspense fallback={<div>Загрузка...</div>}>
                <SmileyFace />
            </Suspense>
        </div>
    );
}
```

**React.lazy работает только с экспортами по умолчанию (default exports)**.

### 2.3. Code Splitting в сборщиках

Для автоматического кодового сплиттинга сборщики (Webpack, Rspack, esbuild) поддерживают настройку, при которой динамические импорты создают отдельные чанки.

**Настройка Rspack для ESM-библиотек (2026):**

```javascript
import { rspack } from "@rspack/core";

export default {
    entry: "./index.js",
    output: {
        chunkFormat: false,
        chunkLoading: 'import',  // Использование динамического import для загрузки чанков
    },
    optimization: {
        runtimeChunk: true,
        concatenateModules: false,
    },
    plugins: [new rspack.experiments.EsmLibraryPlugin()],
};
```

В 2026 году код сплиттинг стал настолько стандартным, что большинство фреймворков (Next.js, Remix, Astro) применяют его автоматически.

### 2.4. Анализ покрытия кода

Для оценки эффективности кодового сплиттинга используется панель **Coverage** в DevTools. Она показывает процент кода, который был реально выполнен во время сессии. Высокий процент неиспользуемого кода указывает на необходимость улучшения сплиттинга.

## 3. Speculation Rules API: упреждающая загрузка страниц (Chromium-only, с оговоркой по Safari)

**Speculation Rules API** — это экспериментальная технология для упреждающей загрузки (prefetch) и предварительного рендеринга (prerender) страниц, на которые пользователь может перейти (подробнее статус поддержки уже разбирался в Главе 11 в контексте интеграции с Navigation API — здесь мы рассматриваем сам API детальнее). В отличие от традиционных `<link rel="prefetch">`, этот API позволяет браузеру более интеллектуально управлять предзагрузкой на основе правил, заданных разработчиком.

### 3.1. Как работает Speculation Rules

Правила спекуляции задаются через тег `<script type="speculationrules">` или заголовок HTTP `Speculation-Rules`:

```html
<script type="speculationrules">
{
    "prefetch": [
        {
            "source": "list",
            "urls": ["/products", "/about", "/contact"],
            "requires": ["anonymous-client-ip-when-cross-origin"]
        }
    ],
    "prerender": [
        {
            "source": "list",
            "urls": ["/dashboard"],
            "eagerness": "moderate"
        }
    ]
}
</script>
```

**Ключевые параметры:**

- **`eagerness`** — определяет, насколько агрессивно браузер должен загружать страницы:
    - **`conservative`** — загрузка только при нажатии (mouse down / touch start). Рекомендуется для безопасного использования в продакшене.
    - **`moderate`** — загрузка при наведении или небольшом скролле.
    - **`eager`** — немедленная загрузка после загрузки текущей страницы.
- **`requires`** — дополнительные требования (например, анонимность для кросс-сайтовых запросов).

### 3.2. Prefetch vs Prerender

| Характеристика | Prefetch | Prerender |
|----------------|----------|-----------|
| **Что загружается** | Только HTML-ответ | HTML + все субресурсы (CSS, JS, изображения) + выполнение JavaScript |
| **Использование ресурсов** | Низкое | Высокое (сравнимо с iframe) |
| **Время активации** | Мгновенное (HTML уже в кеше) | Почти мгновенное (страница уже отрендерена в невидимой вкладке) |
| **Безопасность** | Высокая | Может выполнять аналитику и side-эффекты |
| **Применение** | Все значимые страницы сайта | Только страницы, на которые пользователь точно перейдет |

**Важно:** prefetch загружает только HTML-документ, субресурсы не загружаются до перехода по ссылке. Prerender загружает всю страницу, включая скрипты и изображения.

### 3.3. Поддержка браузерами

На 2026 год Speculation Rules API имеет production-ready реализацию в Chromium-браузерах (Chrome, Edge, Opera) начиная с версии 121 (базовые правила prefetch — заметно раньше, с 108). Firefox официально не реализовал API — команда лишь недавно заняла «positive» позицию по части prefetch, что означает намерение рассмотреть, а не готовую поддержку. С Safari формулировка чуть точнее, чем «игнорирует»: начиная с версии 26.2 в движке есть рабочая реализация API, но она **отключена по умолчанию** — то есть код с `<script type="speculationrules">` в Safari просто не активируется, пока пользователь или сама Apple не включат флаг, а не потому что браузер не знает об этом теге вовсе. Так как API спроектирован как прогрессивное улучшение, отсутствие поддержки нигде не ломает страницу — браузеры без реализации просто игнорируют содержимое тега.

### 3.4. Практические примеры

**Shopify.** Все Liquid-based магазины используют Speculation Rules API с `prefetch` и `conservative` eagerness. Загрузка начинается при нажатии на ссылку (до момента отпускания), что значительно ускоряет навигацию без избыточного использования ресурсов.

**WordPress.** С версии 6.8 имеет встроенную поддержку Speculation Rules через плагин "Speculative Loading". По умолчанию используется `prerender` с `moderate` eagerness для неавторизованных пользователей. Для авторизованных пользователей и администраторов функция может быть включена вручную с учетом дополнительной нагрузки на сервер.

### 3.5. Безопасность и побочные эффекты

**Prerender выполняет JavaScript**, включая аналитические скрипты. Это может привести к:

- Завышению статистики просмотров.
- Выполнению небезопасных действий (например, если ссылка ведет на `/logout` или содержит nonce).

**Рекомендации по безопасности:**

- Исключать из спекулятивной загрузки URL с nonce (`_wpnonce`) и ссылки с `rel="nofollow"`.
- Использовать CSS-класс `no-prerender` для ссылок, которые нельзя пререндерить.
- Для серверной логики перед отправкой правила следует фильтровать URL-пути, исключая потенциально опасные эндпоинты (админку, корзину, формы).

## 4. Рендеринг на стороне сервера (SSR) vs Рендеринг на клиенте (CSR): гибридный подход

Выбор режима рендеринга — одно из ключевых архитектурных решений в 2026 году. Вместо жесткого выбора между SSR и CSR, современные фреймворки поддерживают гибридные подходы, позволяя выбирать оптимальную стратегию для каждой страницы или даже компонента.

### 4.1. Сравнение режимов рендеринга

| Режим | Где рендерится | SEO | TTFB | LCP | Серверная нагрузка |
|-------|---------------|-----|------|-----|-------------------|
| **CSR** | Клиент (браузер) | Плохое | Высокий | Медленный | Минимальная |
| **SSR** | Сервер (на каждый запрос) | Отличное | Средний | Быстрый | Высокая |
| **SSG** | Сервер (при сборке) | Отличное | Очень быстрый | Очень быстрый | Отсутствует |
| **ISR** | Сервер (при сборке + фон) | Отличное | Быстрый | Быстрый | Средняя |

### 4.2. CSR (Client-Side Rendering)

При CSR сервер отправляет минимальный HTML-скелет, а весь контент генерируется в браузере с помощью JavaScript.

**Преимущества:**
- Минимальная серверная нагрузка.
- Интерактивность из коробки (без гидратации).

**Недостатки:**
- Медленный FCP и LCP — браузер должен загрузить, распарсить и выполнить JavaScript, прежде чем показать контент.
- Плохой SEO — поисковые роботы могут не выполнить JavaScript.

### 4.3. SSR (Server-Side Rendering)

При SSR сервер генерирует полный HTML на каждый запрос. Браузер показывает контент сразу, а затем JavaScript "гидратирует" его для интерактивности.

**Преимущества:**
- Быстрый FCP и LCP — пользователь видит контент мгновенно.
- Отличное SEO — контент присутствует в исходном HTML.

**Недостатки:**
- Высокая серверная нагрузка — страница рендерится на сервере для каждого пользователя.
- Более высокий TTFB (время до первого байта) по сравнению с SSG.

### 4.4. SSG (Static Site Generation)

При SSG HTML-страницы генерируются на этапе сборки и раздаются через CDN как статические файлы.

**Преимущества:**
- Максимально быстрый TTFB (< 50 мс).
- Нулевая серверная нагрузка на каждый запрос.
- Идеален для контента, который редко меняется.

**Недостатки:**
- Контент обновляется только при новой сборке.
- Не подходит для персонализированных страниц.

### 4.5. ISR (Incremental Static Regeneration)

ISR сочетает скорость SSG с возможностью обновления контента без полной пересборки. Страница генерируется при сборке, но обновляется в фоне по истечении заданного интервала (revalidate).

```javascript
// Next.js ISR
export async function getStaticProps() {
    const data = await fetchData();
    return {
        props: { data },
        revalidate: 60  // Обновлять каждые 60 секунд
    };
}
```

### 4.6. Гибридный подход в 2026 году

Современные фреймворки (Next.js, Remix, Astro, Nuxt) позволяют комбинировать режимы на уровне маршрутов.

**Next.js App Router:**
- Используйте серверные компоненты для SSR или SSG.
- Используйте `"use client"` для клиентских компонентов.
- Встроенная поддержка ISR через `revalidate`.

**Astro:**
- "Islands Architecture" — статический HTML с изолированными интерактивными "островками", которые гидратируются только при необходимости.

**React Server Components (RSC):**
- Компоненты рендерятся на сервере с нулевым клиентским JavaScript по умолчанию.
- Интерактивные компоненты помечаются `"use client"` и гидратируются как обычно.

### 4.7. Практические рекомендации по выбору режима

| Тип страницы | Рекомендуемый режим | Обоснование |
|--------------|---------------------|-------------|
| Блог, документация | SSG | Контент статичен, важна скорость |
| Интернет-магазин (каталог) | ISR | Контент обновляется редко, нужна скорость |
| Личный кабинет, корзина | SSR | Данные персонализированы и динамичны |
| SPA-приложение с бэкендом | CSR + SSR для SEO | Интерактивность — главное |

### 4.8. Рендеринг и гидратация в 2026

**Гидратация** — процесс, при котором серверный HTML "оживает" с помощью JavaScript.

В 2026 году гидратация стала более избирательной:
- Полная гидратация — для страниц с высокой интерактивностью.
- Частичная гидратация — для страниц с отдельными интерактивными компонентами (Astro, React Server Components).
- "Гидратация с отложенной загрузкой" — гидратация только тех компонентов, которые видны пользователю.

```javascript
// Пример гидратации в библиотеке @dreamer/render (2026)
import { createReactiveRootHydrate } from '@dreamer/render/view-hybrid';

// Гидратация существующего SSR-HTML с последующими обновлениями
const { container, unmount } = createReactiveRootHydrate(
    document.getElementById('app'),
    getState,
    buildTree
);
```

## Итог

Сборка и доставка кода в 2026 году — это многоуровневая система, включающая:

- **ES-модули и Import Maps.** Стандарт для управления зависимостями. Import Maps позволяют использовать голые спецификаторы и управлять версиями зависимостей на уровне браузера. JSON Modules с 2025 года по-настоящему кросс-браузерны (Chrome, Firefox 128+, Safari), а вот CSS Modules остаются Chromium-only — эти два похожих механизма стоит различать по зрелости.
- **Динамический импорт и код-сплиттинг.** `import()` позволяет лениво загружать код по требованию. React.lazy и Suspense интегрируют эту возможность с компонентной моделью. Сборщики (Rspack, Webpack, esbuild) поддерживают автоматическое разделение чанков.
- **Speculation Rules API.** Механизм для упреждающей загрузки страниц с production-ready статусом в Chromium. Firefox не реализовал API вовсе, Safari содержит реализацию, но отключённую по умолчанию. Prefetch загружает HTML, Prerender — всю страницу включая субресурсы. Используется в производственной среде крупными платформами (Shopify, WordPress) для ускорения навигации — там, где браузер поддерживает API; в остальных случаях страница просто работает без ускорения.
- **Гибридный рендеринг.** Современные фреймворки позволяют выбирать между CSR, SSR, SSG и ISR на уровне маршрутов. React Server Components и Islands Architecture делают гибридный подход стандартом 2026 года, где контент рендерится на сервере, а интерактивность — на клиенте.
