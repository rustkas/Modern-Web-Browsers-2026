# Глава 9. Современная сетевая модель (HTTP/3 и QUIC)

В 2026 году сетевая подсистема браузера представляет собой сложный, высокооптимизированный механизм, который обеспечивает не просто передачу данных, а интеллектуальное управление соединениями, адаптацию под состояние сети и жесткий контроль над каждым запросом. Сетевой стек браузера больше не является "черным ящиком", а стал управляемой и прозрачной частью платформы.

Эта глава последовательно разбирает три ключевых аспекта современной сетевой модели: механизмы управления запросами через Fetch API, принципы работы протокола HTTP/3 и технологию 0-RTT, а также инструменты для адаптации приложений под изменяющиеся сетевые условия.

---

## 1. Fetch API 2026: новый контроллер сигналов и таймаутов

Fetch API остается основным интерфейсом для выполнения сетевых запросов. В 2026 году его ключевым улучшением стала стандартизация и широкое распространение механизмов управления жизненным циклом запроса через `AbortSignal` и встроенную поддержку таймаутов.

### 1.1. AbortSignal: управление отменой запросов

`AbortSignal` представляет собой объект, который позволяет передать сигнал об отмене асинхронной операции, такой как fetch-запрос . Он работает в связке с `AbortController`: контроллер создает сигнал и предоставляет метод `abort()` для его активации.

При инициализации fetch-запроса разработчик может передать сигнал в опции запроса . Это связывает жизненный цикл запроса с сигналом: если сигнал переходит в состояние "отменен", fetch-запрос прерывается, а его promise отклоняется с ошибкой `AbortError` .

```javascript
// Базовый паттерн с AbortController
const controller = new AbortController();
const signal = controller.signal;

// Запуск запроса с возможностью отмены
fetch('https://api.example.com/data', { signal })
  .then(response => response.json())
  .catch(error => {
    if (error.name === 'AbortError') {
      console.log('Запрос отменен пользователем');
    }
  });

// Отмена запроса
controller.abort();
```

### 1.2. Автоматические таймауты через AbortSignal.timeout()

В 2026 году стандартным способом установки таймаута для fetch-запроса является статический метод `AbortSignal.timeout(ms)`. Он возвращает сигнал, который автоматически переходит в состояние "отменен" через указанное количество миллисекунд .

Этот метод, доступный во всех современных браузерах с 2024 года , решает проблему "зависших" запросов. Без таймаута запрос может висеть бесконечно, блокируя ресурсы и ухудшая пользовательский опыт .

```javascript
// Автоматический таймаут через 5 секунд
try {
  const response = await fetch('https://api.example.com/data', {
    signal: AbortSignal.timeout(5000)
  });
  const data = await response.json();
} catch (error) {
  if (error.name === 'TimeoutError') {
    console.error('Запрос превысил лимит времени (5 секунд)');
    // Показываем пользователю сообщение о таймауте
  } else if (error.name === 'AbortError') {
    console.error('Запрос отменен пользователем');
  }
}
```

**Важное различие:** `AbortSignal.timeout()` генерирует `TimeoutError`, а не `AbortError`. Это позволяет различать ситуации таймаута и ручной отмены запроса .

### 1.3. Комбинирование сигналов

В сложных сценариях может потребоваться комбинировать несколько источников отмены: например, таймаут и возможность ручной отмены пользователем. Для этого используется `AbortSignal.any()`, который объединяет несколько сигналов в один .

```javascript
// Комбинирование таймаута и ручной отмены
const userController = new AbortController();

const combinedSignal = AbortSignal.any([
  userController.signal,
  AbortSignal.timeout(10000) // 10 секунд
]);

try {
  const response = await fetch('https://api.example.com/large-file', {
    signal: combinedSignal
  });
  // Обработка ответа...
} catch (error) {
  if (error.name === 'TimeoutError') {
    console.log('Таймаут 10 секунд');
  } else if (error.name === 'AbortError') {
    console.log('Отменено пользователем');
  }
}
```

### 1.4. Практический паттерн: защита внешних вызовов

Для бэкенд-сервисов, выполняющих внешние HTTP-запросы (например, в среде Node.js с `fetch`), таймауты стали обязательным паттерном. Без таймаута медленный внешний API может заблокировать обработку запроса клиента .

```javascript
// Express-маршрут с защитой от таймаута
app.get('/dashboard', async (req, res, next) => {
  try {
    const data = await fetchJSON('https://api.example.com/report', {
      signal: AbortSignal.timeout(3000) // 3 секунды
    });
    res.json(data);
  } catch (error) {
    if (error.name === 'TimeoutError') {
      res.status(504).json({ error: 'Внешний API не отвечает' });
      return;
    }
    next(error);
  }
});
```

## 2. HTTP/3 и 0-RTT: как браузер ускоряет соединения

HTTP/3 — это третья версия протокола HTTP, работающая поверх IETF QUIC . В отличие от HTTP/2, который использует TCP, HTTP/3 построен на основе протокола QUIC, работающего поверх UDP. Это фундаментальное изменение решает проблемы "головной блокировки" (Head-of-Line Blocking) и ускоряет установку соединений.

### 2.1. 0-RTT (Zero Round Trip Time): мгновенное соединение

**0-RTT** — одна из ключевых возможностей QUIC, позволяющая клиенту отправлять данные на сервер при установке нового соединения без дополнительного обмена пакетами .

**Как это работает:**

1. При первом соединении клиент и сервер обмениваются ключами шифрования и сохраняют "секрет" (сессионный ключ).
2. При повторном соединении клиент использует сохраненный секрет для отправки зашифрованных данных ("ранних данных") вместе с первым пакетом установки соединения.
3. Сервер получает данные одновременно с рукопожатием, что экономит одно полное время往返 (RTT).

**Когда 0-RTT работает:**

- Только при повторных соединениях между клиентом и сервером.
- Только для **безопасных** запросов (GET, HEAD, OPTIONS, TRACE). Небезопасные методы (POST, PUT, DELETE) не отправляются через 0-RTT.
- 0-RTT может не сработать по разным причинам (изменение ключей, миграция сервера), и браузер переключится на обычный 1-RTT .

**Преимущества:**

- Сокращение времени загрузки страниц (Google Search latency снизилась после включения HTTP/3 ).
- Меньше задержек для видео (YouTube уменьшил число перебуферизаций).

### 2.2. ORIGIN Frame: оптимизация пулов соединений

**ORIGIN Frame** (RFC 9412) позволяет серверу сообщать клиенту, для каких доменов он авторитетен и хотел бы использовать одно соединение .

**Проблема без ORIGIN Frame:**

- Браузер устанавливает соединение с `example.com`.
- Сервер имеет сертификат для `example.com`, `api.example.com` и `cdn.example.com`.
- Браузер не может использовать это соединение для `api.example.com`, не выполнив DNS-запрос к `api.example.com` и не проверив IP-адрес на совпадение с существующим соединением.
- Эта проверка не всегда проходит: по данным Chrome, почти 20% HTTP/3-соединений оказываются избыточными из-за несовпадения IP-адресов .

**Решение с ORIGIN Frame:**

Сервер отправляет ORIGIN Frame, перечисляя все домены, для которых он может обслуживать запросы. Браузер может отправлять запросы к этим доменам через уже установленное соединение без дополнительных DNS-запросов . Это снижает:

- Задержку (DNS разрешение).
- Использование памяти и CPU (одно соединение против нескольких).
- Накладные расходы на установку соединений.

### 2.3. Server's Preferred Address: оптимизация маршрутов

**Server's Preferred Address** (RFC 9000 Section 9.6) позволяет серверу указать клиенту, что он хотел бы мигрировать на другой IP-адрес .

**Сценарий использования:**

- Клиент подключается к серверу через маршрутизатор L4.
- Маршрутизатор может находиться далеко от сервера, создавая "трехногий" путь (клиент → маршрутизатор → сервер → маршрутизатор → клиент), что увеличивает RTT .
- После завершения рукопожатия сервер указывает предпочтительный адрес (например, напрямую IP-адрес сервера), предлагая клиенту мигрировать на него.

**Результаты в Chrome:** миграция успешна в более чем 99% случаев и снижает средний RTT на 40–80% . На момент 2026 года основной сценарий внедрения — Google's Media CDN, но ожидается более широкое принятие.

## 3. Network Information API: адаптация под медленные сети

**Network Information API** предоставляет веб-приложениям информацию о качестве текущего сетевого соединения. Это позволяет приложениям адаптироваться к условиям сети: загружать изображения меньшего размера, уменьшать качество видео или отключать ресурсоемкие функции .

### 3.1. Ключевые свойства NetworkInformation

Интерфейс `NetworkInformation` предоставляет следующие свойства :

- **`type`** (ConnectionType): Тип соединения: `"bluetooth"`, `"cellular"`, `"ethernet"`, `"wifi"`, `"wimax"`, `"other"`, `"none"`.
- **`effectiveType`** (EffectiveConnectionType): Агрегированное качество соединения на основе наблюдаемых задержки и пропускной способности. Значения: `"slow-2g"`, `"2g"`, `"3g"`, `"4g"` .
- **`rtt`** (Milliseconds): Оценочное значение RTT (Round-Trip Time) в миллисекундах.
- **`downlink`** (Mbps): Оценочная пропускная способность вниз (мегабит в секунду).
- **`downlinkMax`** (Mbps): Максимальная пропускная способность для типа соединения.

**Пороговые значения `effectiveType` (на основе реальных измерений Chrome на Android, 2017) :**

| Тип | Максимальный RTT (мс) | Максимальный downlink (Kbps) |
|-----|----------------------|------------------------------|
| `slow-2g` | 2000 | 50 |
| `2g` | 1400 | 70 |
| `3g` | 270 | 700 |
| `4g` | 0 (без ограничений) | ∞ (без ограничений) |

### 3.2. Использование API для адаптации контента

```javascript
// Получение объекта NetworkInformation
const connection = navigator.connection;

// Чтение текущего состояния
console.log(`Тип: ${connection.type}`);
console.log(`Эффективный тип: ${connection.effectiveType}`);
console.log(`RTT: ${connection.rtt} мс`);
console.log(`Пропускная способность: ${connection.downlink} Mbps`);

// Адаптация ресурсов
function loadImage() {
    if (connection.effectiveType === '4g') {
        // Загрузка изображения высокого разрешения
        loadFullQualityImage();
    } else if (connection.effectiveType === '3g') {
        // Загрузка изображения среднего качества
        loadMediumQualityImage();
    } else {
        // slow-2g или 2g: загрузка миниатюры
        loadThumbnailImage();
    }
}

// Реакция на изменения сети
connection.addEventListener('change', () => {
    console.log('Состояние сети изменилось');
    // Переадаптация контента
    loadImage();
});
```

### 3.3. Ограничения API

- **Оценка, а не абсолютное значение.** Значения RTT и downlink — это оценки, основанные на наблюдениях браузера. Они не являются точными измерениями в реальном времени.
- **Доступность.** API доступен в `Window` и `Worker` контекстах, но не во всех браузерах и может быть ограничен политикой безопасности.
- **Фингерпринтинг.** API может использоваться для создания цифрового отпечатка устройства, что вызвало дебаты о его доступности. В некоторых браузерах он может быть ограничен или требовать разрешения.

### 3.4. Практический паттерн: адаптивная загрузка

```javascript
// Адаптивная загрузка видео в зависимости от сети
function getVideoQuality() {
    const effectiveType = navigator.connection?.effectiveType || '4g';
    
    switch (effectiveType) {
        case 'slow-2g':
        case '2g':
            return { src: 'video-low.mp4', bitrate: '200kbps' };
        case '3g':
            return { src: 'video-medium.mp4', bitrate: '800kbps' };
        case '4g':
        default:
            return { src: 'video-high.mp4', bitrate: '4Mbps' };
    }
}

// Использование
const videoQuality = getVideoQuality();
document.querySelector('video').src = videoQuality.src;
```

## Итог

Современная сетевая модель браузера 2026 года — это многоуровневая система, обеспечивающая гибкость, производительность и адаптивность:

- **Fetch API** предоставляет развитые механизмы управления запросами через `AbortSignal`. Статический метод `AbortSignal.timeout()` является стандартным способом установки таймаутов, защищающим приложения от зависших запросов. Комбинирование сигналов через `AbortSignal.any()` позволяет создавать сложную логику отмены.
- **HTTP/3 и QUIC** радикально ускоряют сетевые взаимодействия. Технология **0-RTT** позволяет отправлять данные при установке соединения, экономя время往返. **ORIGIN Frame** оптимизирует пулы соединений, снижая накладные расходы. **Server's Preferred Address** позволяет мигрировать на оптимальный маршрут, сокращая RTT до 80%.
- **Network Information API** дает приложениям информацию о качестве соединения (`effectiveType`, `rtt`, `downlink`), позволяя адаптировать загрузку ресурсов под условия сети, что критично для мобильных устройств и регионов с медленным интернетом.

В следующей главе мы рассмотрим Service Workers — технологию, которая позволяет приложениям работать офлайн, кешировать ресурсы и перехватывать сетевые запросы, действуя как прокси-сервер внутри браузера.
