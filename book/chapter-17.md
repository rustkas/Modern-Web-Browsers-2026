# Глава 17. WebTransport и WebCodecs

В 2026 году две технологии окончательно сформировали новый слой браузерных возможностей для работы с сетью и мультимедиа: **WebTransport** — преемник WebSocket, построенный на HTTP/3 и QUIC, — стал стандартом **Baseline (март 2026)** , а **WebCodecs** — API для низкоуровневого аппаратно-ускоренного кодирования и декодирования — достиг статуса **Near-Baseline** . Эти технологии позволяют веб-приложениям работать с низкоуровневыми сетевыми протоколами и медиапотоками с производительностью, ранее недоступной в браузере.

Эта глава последовательно разбирает: что такое WebTransport, чем он лучше WebSocket, как он работает с мультиплексированием и датаграммами; устройство WebCodecs и его применение для обработки видео и аудио на лету; а также практические сценарии совместного использования этих API.

---

## 1. WebTransport: замена WebSocket

### 1.1. Проблемы WebSocket

WebSocket долгое время был стандартным решением для двунаправленной связи в вебе. Однако он имеет фундаментальные ограничения:

- **Единый поток.** WebSocket работает поверх одного TCP-соединения, где все сообщения передаются последовательно. Если один пакет потерян, все последующие задерживаются до его повторной передачи — это называется **Head-of-Line (HoL) blocking** (блокировка головы очереди) . В результате даже небольшой сбой в сети может вызвать заметные задержки для всех данных, передаваемых по соединению.
- **Только надежная доставка.** WebSocket не поддерживает ненадежную передачу (датаграммы). Для сценариев, где допустима потеря части данных ради скорости (игровой ввод, позиция курсора), приходится использовать WebRTC DataChannel со всеми его сложностями.
- **Один RTT для установки.** Установка WebSocket-соединения требует как минимум один полный цикл обмена (Round-Trip Time, RTT) плюс время на TLS-рукопожатие, что добавляет задержку при каждом подключении.

### 1.2. Архитектура WebTransport

WebTransport — это API, который позволяет веб-приложениям устанавливать интерактивные, двунаправленные, мультиплексированные сетевые соединения . Он использует HTTP/3 и протокол QUIC, который работает поверх UDP .

**Ключевые возможности WebTransport:**

- **Надежная передача через потоки.** Поддерживает двунаправленные и однонаправленные потоки с гарантированной доставкой и порядком, как в WebSocket, но без HoL-блокировки — сбой в одном потоке не влияет на другие .
- **Ненадежная передача через датаграммы.** Отправка небольших сообщений без гарантии доставки или порядка, с минимальной задержкой. Идеально для игрового ввода, позиции объектов, телеметрии .
- **Мультиплексирование.** Несколько логических потоков данных поверх одного физического соединения, что снижает накладные расходы на установку соединений .
- **0-RTT (Zero Round-Trip Time).** При повторном подключении к знакомому серверу данные могут быть отправлены в первом же пакете, без дополнительного рукопожатия — экономия полного RTT .
- **Миграция соединений.** QUIC использует уникальные идентификаторы соединений (connection IDs), которые сохраняются при смене IP-адреса. Загрузка не прерывается при переключении с Wi-Fi на мобильную сеть .
- **Без NAT Traversal.** В отличие от WebRTC, WebTransport не требует ICE/STUN/TURN для обхода NAT, так как это клиент-серверная модель, а не P2P .

### 1.3. Статус поддержки (2026)

В марте 2026 года, когда Safari 26.4 добавил поддержку, WebTransport стал **Baseline** — доступен во всех современных браузерах :

- **Chrome / Edge:** стабильная поддержка с версии 97 (январь 2022), без флагов.
- **Firefox:** стабильная поддержка с версии 114 (июнь 2023).
- **Safari:** стабильная поддержка с версии 26.4 (март 2026) .

API доступен только в безопасном контексте (HTTPS) и поддерживает работу в Web Workers . В 2026 году он используется в продакшене на платформах Cloudflare (Workers + Durable Objects), в системах облачного гейминга и удаленного рабочего стола, а также в стриминговых платформах для sub-500ms доставки видео .

### 1.4. Использование WebTransport

**Установка соединения:**

```javascript
// Открытие соединения к HTTP/3 серверу
const transport = new WebTransport('https://example.com:4433');

// Ожидание готовности соединения
await transport.ready;
console.log('Соединение установлено');
```

**Отправка датаграмм (ненадежная передача):**

```javascript
// Отправка небольших сообщений с минимальной задержкой
const writer = transport.datagrams.writable.getWriter();
const data = new Uint8Array([1, 2, 3, 4]);
await writer.write(data);

// Получение датаграмм
const reader = transport.datagrams.readable.getReader();
for await (const chunk of reader) {
    console.log('Получена датаграмма:', chunk);
}
```

**Создание надежного двунаправленного потока:**

```javascript
// Создание потока
const stream = await transport.createBidirectionalStream();
const writer = stream.writable.getWriter();
const reader = stream.readable.getReader();

// Отправка данных
await writer.write(new Uint8Array([1, 2, 3]));
await writer.close();

// Получение ответа
const { value, done } = await reader.read();
console.log('Ответ:', value);
```

**Создание однонаправленного потока (только отправка):**

```javascript
// Отправка без ожидания ответа
const sendStream = await transport.createUnidirectionalStream();
const writer = sendStream.writable.getWriter();
await writer.write(new Uint8Array([4, 5, 6]));
await writer.close();
```

### 1.5. Производительность и сценарии использования

WebTransport обеспечивает снижение задержки на 30–50% по сравнению с WebSocket на мобильных сетях с потерями пакетов . Это связано с устранением HoL-блокировки и использованием 0-RTT . В 2026 году WebTransport используется в следующих сценариях:

- **Живые медиа.** Миграция с LL-HLS на WebTransport для задержки < 500 мс .
- **Облачный гейминг и удаленный рабочий стол.** Датаграммы для ввода и подтверждений кадров, надежные потоки для управления .
- **Чат и уведомления.** Более эффективное управление соединениями благодаря мультиплексированию .
- **Передача файлов.** Надежные потоки для больших файлов без HoL-блокировки .

**Когда использовать WebTransport:** когда вы контролируете и клиент, и сервер, ваш CDN поддерживает HTTP/3 (Cloudflare, Fastly, Akamai) и ваша аудитория может позволить себе fallback на WebSocket в сетях, блокирующих UDP .

**Когда подождать:** если ваш трафик идет через корпоративные сети со строгими UDP-правилами (сложность fallback может перевесить выгоду) или существующий WebSocket-стек уже удовлетворяет требованиям по задержке .

## 2. WebCodecs: кодирование и декодирование на лету

WebCodecs API позволяет веб-разработчикам эффективно (с использованием аппаратного ускорения) и с очень низкоуровневым контролем (обработка покадрово) кодировать и декодировать видео и аудио в браузере . Он предоставляет доступ к встроенным медиакомпонентам браузера, устраняя необходимость перепаковывать кодеки в WebAssembly .

### 2.1. Ключевые интерфейсы WebCodecs

WebCodecs определяет следующие основные интерфейсы :

- **Видео:**
  - `VideoFrame` — представляет один кадр несжатого видео с пиксельными данными в памяти GPU. Является `CanvasImageSource` и может использоваться в `drawImage()` и `texImage2D()` .
  - `EncodedVideoChunk` — представляет сжатый (закодированный) кадр видео. Содержит двоичные данные и метку типа: `"key"` (ключевой кадр, независимый от других) или `"delta"` .
  - `VideoEncoder` — кодирует `VideoFrame` → `EncodedVideoChunk` .
  - `VideoDecoder` — декодирует `EncodedVideoChunk` → `VideoFrame` .

- **Аудио:**
  - `AudioData` — представляет блок несжатых аудиосэмплов (обычно 1024 сэмпла) .
  - `EncodedAudioChunk` — представляет сжатый аудиоблок.
  - `AudioEncoder` — кодирует `AudioData` → `EncodedAudioChunk` .
  - `AudioDecoder` — декодирует `EncodedAudioChunk` → `AudioData` .

### 2.2. Архитектура и производительность

**Асинхронная модель.** WebCodecs использует асинхронную модель обработки. Каждый экземпляр кодера/декодера содержит внутреннюю очередь. Методы `encode()` и `decode()` возвращаются немедленно, а результаты приходят через колбэки `output` и `error` . Это позволяет держать кодер/декодер загруженным и эффективно использовать аппаратное ускорение . Метод `flush()` позволяет дождаться завершения всех операций в очереди .

**Аппаратное ускорение.** WebCodecs использует аппаратные кодеки операционной системы через платформенные API (например, VideoToolbox на macOS, MediaCodec на Android). Это обеспечивает кодирование/декодирование с низким энергопотреблением и высокой производительностью .

**Работа в Web Workers.** WebCodecs спроектирован для работы вне основного потока. `VideoFrame` является transferable, что позволяет перемещать кадры между Worker'ами без копирования . В 2026 году большинство продакшн-реализаций выносят обработку видео в Web Workers .

**Статус поддержки (2026):**

- **Chrome / Edge:** стабильно с версии 94 (сентябрь 2021).
- **Safari:** полная поддержка (включая аудио) с версии 26 (сентябрь 2025); видео — с 16.4 (март 2023) .
- **Firefox:** декодирование и большая часть кодирования на десктопе — с 2024 года; Android пока отсутствует .

В 2026 году WebCodecs используется в продакшене: Zoom Web Client перестроен на WebCodecs + WebAssembly + WebTransport, Loom использует для кодирования и обрезки видео с ускорением ~10x по сравнению с `MediaRecorder`, Discord использует для H.264-энкодинга в screen-share, Adobe Premiere Web использует для превью на клиенте .

### 2.3. Пример кодирования видео (схема)

```javascript
// Проверка поддержки конфигурации
const config = {
    codec: 'vp8',
    width: 640,
    height: 480,
    bitrate: 2_000_000, // 2 Mbps
    framerate: 30,
};

const { supported } = await VideoEncoder.isConfigSupported(config);
if (!supported) {
    // Попробовать другой кодек (например, 'avc1.4d0034' для H.264)
}

// Создание и настройка энкодера
const encoder = new VideoEncoder({
    output: (chunk, metadata) => {
        // Отправка закодированного чанка на сервер
        if (metadata.decoderConfig) {
            // Отправка конфигурации декодеру
        }
        sendChunkToServer(chunk);
    },
    error: (e) => console.error(e.message),
});

encoder.configure(config);

// Получение кадров с камеры через MediaStreamTrackProcessor
const trackProcessor = new MediaStreamTrackProcessor(
    await navigator.mediaDevices.getUserMedia({ video: true })
);

let frameCounter = 0;
for await (const frame of trackProcessor.readable) {
    if (encoder.encodeQueueSize > 2) {
        // Энкодер перегружен — пропускаем кадр
        frame.close();
        continue;
    }

    const keyFrame = frameCounter % 150 === 0;
    encoder.encode(frame, { keyFrame });
    frame.close();
    frameCounter++;
}

// Ожидание завершения всех операций
await encoder.flush();
encoder.close();
```

### 2.4. Пример декодирования видео

```javascript
// Проверка поддержки конфигурации
const config = {
    codec: 'vp8',
    codedWidth: 640,
    codedHeight: 480,
};

const { supported } = await VideoDecoder.isConfigSupported(config);

// Создание и настройка декодера
const decoder = new VideoDecoder({
    output: (frame) => {
        // Отображение декодированного кадра на canvas
        const canvas = document.getElementById('canvas');
        const ctx = canvas.getContext('2d');
        ctx.drawImage(frame, 0, 0);
        frame.close();
    },
    error: (e) => console.error(e.message),
});

decoder.configure(config);

// Получение закодированных чанков (например, с сервера по WebTransport)
for await (const chunk of receiveVideoChunks()) {
    decoder.decode(chunk);
}
await decoder.flush();
decoder.close();
```

### 2.5. Аудио: пример кодирования Opus

В 2026 году WebCodecs активно используется для кодирования аудио в речивых AI-агентах, работающих в реальном времени (OpenAI Realtime, Gemini Live API) . Схема: захват через AudioWorklet с размером шага 20 мс → преобразование в `AudioData` → кодирование через `AudioEncoder` с кодеком `opus` → отправка по WebSocket или WebTransport.

```javascript
const encoder = new AudioEncoder({
    output: (chunk) => sendToServer(chunk),
    error: (e) => console.error(e),
});

encoder.configure({
    codec: 'opus',
    sampleRate: 16000,
    numberOfChannels: 1,
    bitrate: 16000, // 16 kbps для речи
    bitrateMode: 'constant',
});

// Прием AudioData от AudioWorklet и кодирование
const audioData = getAudioDataFromMicrophone();
encoder.encode(audioData);
audioData.close();

await encoder.flush();
```

### 2.6. Ограничения

- **Кодеки отличаются по платформам.** AV1-энкодирование доступно только в Chrome на 2026 год .
- **Firefox Android** полностью не поддерживает WebCodecs .
- **Мультиплексирование (muxing) не встроено.** WebCodecs работает с отдельными чанками, но не умеет упаковывать их в `.mp4` или `.webm`. Для этого нужны библиотеки, например, **Mediabunny** или **web-demuxer** .
- **HEVC-кодирование** требует лицензии платформы + поддержки на устройстве .

## 3. Связка WebTransport + WebCodecs: сценарии

В 2026 году WebTransport и WebCodecs часто используются вместе как альтернатива WebRTC для клиент-серверных потоковых приложений . Архитектура выглядит так:

1. **Захват.** `getUserMedia` → `MediaStreamTrack` .
2. **Обработка.** `MediaStreamTrackProcessor` → `VideoFrame` / `AudioData` .
3. **Кодирование.** `VideoEncoder` / `AudioEncoder` → `EncodedVideoChunk` / `EncodedAudioChunk` .
4. **Передача.** WebTransport датаграммы или надежные потоки .
5. **Декодирование на сервере.** Восстановление и дальнейшая обработка или пересылка .

Meta (facebookexperimental/webcodecs-capture-play) и Twitch/YouTube Live используют эту схему для достижения sub-1-second glass-to-glass задержки . В 2026 году WebTransport и WebCodecs вместе являются альтернативой WebRTC для случаев, когда браузер является клиентом, сервер — назначением, а разработчик хочет контролировать медиа-пайплайн самостоятельно и может отказаться от нативной поддержки WebRTC-медиа .

**Когда использовать связку WebTransport + WebCodecs:**

- Вы контролируете и клиент, и сервер (B2B, внутренние инструменты, специальные приложения) .
- Вам нужна задержка < 500 мс, сравнимая с WebRTC, но без WebRTC-оверхеда .
- Вы хотите кастомизировать энкодер, адаптировать качество под сеть в реальном времени .
- Это не massive consumer-приложение, где широкая совместимость (все браузеры + legacy-устройства) — главный приоритет.

## Итог

WebTransport — это современная замена WebSocket, работающая на HTTP/3/QUIC. В марте 2026 года он стал **Baseline** . Он обеспечивает мультиплексирование, надежные потоки и ненадежные датаграммы, отсутствие HoL-блокировки, 0-RTT и миграцию соединений . Он быстрее WebSocket на 30–50% в нестабильных сетях .

WebCodecs — это API для низкоуровневого, аппаратно-ускоренного кодирования и декодирования видео/аудио. В 2026 году он **Near-Baseline** . Он предоставляет покадровый контроль, работает в Web Workers, используется в Zoom, Loom, Discord и Adobe Premiere Web. Требует проверки поддержки кодеков через `isConfigSupported()` .

Связка WebTransport + WebCodecs позволяет создавать клиент-серверные приложения с низкой задержкой без использования WebRTC, от облачного гейминга до стриминга и AI-агентов с обработкой аудио в реальном времени.
