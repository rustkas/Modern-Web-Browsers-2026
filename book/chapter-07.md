# Глава 7. WebNN (Web Neural Network) — ИИ в каждом браузере?

В 2026 году выполнение нейросетевых моделей в браузере действительно перестало быть чистой лабораторной идеей — но, забегая вперёд, оговоримся сразу: заголовок этой главы стоит читать со знаком вопроса. WebNN (Web Neural Network API) — это стандарт W3C, предоставляющий веб-приложениям низкоуровневый доступ к аппаратным ускорителям машинного обучения: CPU, GPU и специализированным NPU/TPU. Но статус технологии в 2026 году гораздо скромнее, чем можно подумать по названию главы, и это стоит понимать перед тем, как читать про архитектуру API.

22 января 2026 года спецификация WebNN действительно достигла статуса Candidate Recommendation — это подтверждённый факт. Но с фактической поддержкой в браузерах дело обстоит куда скромнее: Chrome открыл Origin Trial для тестирования API на реальных пользователях (диапазон версий M147–M149), а вот **Firefox и Safari WebNN на 2026 год не реализовали** — Mozilla официально обозначила лишь намерение реализовать API в будущем, но никакой рабочей поддержки (в том числе «через ONNX Runtime Web», как иногда ошибочно пишут) в Firefox нет: ONNX Runtime Web использует WebNN как execution provider, обращаясь к нативному `navigator.ml`, которого в Firefox просто не существует — без самого API в браузере библиотека не может «добавить» его снаружи. Независимые технологические обзоры сходятся на том, что реалистичный прогноз выхода WebNN в продакшн-готовое состояние — это 2027 год, не 2026-й. Рабочий стек для браузерного ML в 2026 году — это WebGPU в связке с transformers.js или ONNX Runtime Web с WebGPU execution provider, о чём уже говорилось во Введении.

С учётом этой оговорки эта глава детально разбирает архитектуру WebNN, его модель работы с аппаратными ускорителями, форматы моделей и практические сценарии применения — все они технически корректны и стоят изучения на будущее, но воспринимайте их как раздел про технологию на подходе, а не про то, что уже работает у ваших пользователей сегодня.

## 1. Использование NPU/TPU через стандарт WebNN API

WebNN — это API, спроектированный специально для **инференса** (выполнения уже обученных моделей), а не для обучения. Его задача — предоставить унифицированный, независимый от платформы интерфейс к ML-возможностям операционной системы и аппаратному обеспечению.

### 1.1. Модель программирования WebNN

WebNN следует двухэтапной модели:

**Этап 1: Построение вычислительного графа.** Разработчик использует `MLGraphBuilder` API для определения структуры модели: операции (слои), их входы, выходы и параметры (веса). Все операции строятся в виде графа, который затем компилируется в оптимизированный исполняемый граф.

```javascript
// Построение простого графа
const builder = new MLGraphBuilder(context);
const input = builder.input('input', { dataType: 'float32', dimensions: [1, 784] });
const weights = builder.constant({ dataType: 'float32', dimensions: [784, 128] }, weightData);
const bias = builder.constant({ dataType: 'float32', dimensions: [128] }, biasData);

const dense = builder.add(builder.matmul(input, weights), bias);
const output = builder.sigmoid(dense);
```

**Этап 2: Компиляция и выполнение.** Построенный граф компилируется в `MLGraph` — исполняемый объект, оптимизированный под конкретное аппаратное обеспечение. Затем разработчик передает входные данные и запускает выполнение:

```javascript
// Компиляция
const graph = await builder.build();

// Выполнение
const inputs = { 'input': inputTensor };
const outputs = await context.compute(graph, inputs);
```

### 1.2. Выбор аппаратного ускорителя

WebNN автоматически определяет доступные аппаратные ускорители и выбирает наиболее подходящий для выполнения модели. Спецификация WebNN предоставляет механизм выбора устройств через `MLContext`:

```javascript
// Создание контекста с автоматическим выбором устройства
const context = await navigator.ml.createContext();

// Явный выбор устройства (экспериментально, в зависимости от реализации)
const context = await navigator.ml.createContext({
    deviceType: 'npu' // или 'gpu', 'cpu'
});
```

### 1.3. NPU: ключевое преимущество WebNN

Ключевое отличие WebNN от WebGPU — доступ к **NPU (Neural Processing Unit)**, специализированному чипу для выполнения ИИ-нагрузок.

Сравнение NPU и GPU для ИИ-задач:

| Характеристика | GPU | NPU |
|---------------|-----|-----|
| **Архитектура** | Универсальные ядра для графики | Специализированные ядра для нейросетей |
| **Энергопотребление** | Высокое (десятки ватт) | Низкое (единицы ватт) |
| **Эффективность для INT8** | Умеренная | Оптимальная (5-10x лучше GPU) |
| **Типичные задачи** | 3D-графика, GPGPU | Инференс нейросетей |

Стоит подчеркнуть: это преимущество остаётся теоретическим для веб-разработчика, пока WebNN не вышел за пределы Origin Trial. Доступ к NPU из браузера сегодня на практике получить нельзя — ни через WebNN (не готов), ни через WebGPU (не имеет доступа к NPU по архитектуре самого API, только к GPU).

### 1.4. MLTensor API: обмен буферами с WebGPU

Одно из важнейших нововведений спецификации WebNN — **MLTensor API**, который должен позволить разделять буферы памяти между WebNN и WebGPU. Это критически важно для приложений, которые используют WebGPU для предобработки изображений и WebNN для запуска нейросетей, без копирования данных между GPU и CPU:

```javascript
// Создание тензора WebGPU
const tensor = await context.createTensor({
    dataType: 'float32',
    dimensions: [1, 3, 224, 224]
});

// Использование этого же буфера в WebNN
// (MLTensor разделяет память с WebGPU)
const outputs = await context.compute(graph, { input: tensor });
```

Идея устраняет накладные расходы на копирование данных между разными вычислительными устройствами и в перспективе должна сделать пайплайны обработки в реальном времени значительно более эффективными — но, как и остальной WebNN, MLTensor пока доступен только в рамках экспериментальной реализации Chrome.

## 2. Запуск моделей (ONNX, TensorFlow Lite)

WebNN — это низкоуровневый API, ориентированный на выполнение нейросетевых операций. Он не предоставляет встроенных средств для загрузки и парсинга моделей. Разработчик обязан использовать специализированные библиотеки (ONNX Runtime Web, LiteRT/TensorFlow Lite) или загружать веса и строить граф вручную.

### 2.1. Поддерживаемые форматы моделей

Благодаря экосистеме инструментов, WebNN проектируется с расчётом на поддержку популярных форматов моделей:

- **ONNX (Open Neural Network Exchange).** Основной формат, поддерживаемый ONNX Runtime Web с использованием WebNN Execution Provider.
- **TensorFlow Lite (TFLite).** Поддерживается через LiteRT (библиотеку, ранее известную как TensorFlow Lite Web).
- **Другие форматы через конвертеры.** Модели из PyTorch, Keras и других фреймворков конвертируются в ONNX или TFLite.

### 2.2. ONNX Runtime Web с WebNN

Наиболее распространённый способ работы с моделями через WebNN (там, где API вообще доступен — то есть пока только в Chrome с флагом или в рамках Origin Trial) — использование ONNX Runtime Web с WebNN в качестве бэкенда:

```javascript
import * as ort from 'onnxruntime-web';

// Создание сессии с WebNN
const session = await ort.InferenceSession.create('model.onnx', {
    executionProviders: ['webnn']
});

// Выполнение инференса
const feeds = { 'input': new ort.Tensor('float32', inputData, [1, 3, 224, 224]) };
const results = await session.run(feeds);
```

Для продакшн-кода на 2026 год этот вызов обязательно должен быть обёрнут в проверку доступности и fallback на WebGPU execution provider — иначе приложение просто не будет работать за пределами Chrome:

```javascript
const executionProviders = ('ml' in navigator)
  ? ['webnn', 'webgpu', 'wasm']   // Chrome с доступным WebNN
  : ['webgpu', 'wasm'];           // Firefox, Safari — WebNN недоступен

const session = await ort.InferenceSession.create('model.onnx', { executionProviders });
```

### 2.3. onnx2webnn: конвертер моделей ONNX в нативный код WebNN

В экосистеме WebNN существует инструмент **`onnx2webnn`**, который конвертирует модели формата ONNX непосредственно в JavaScript-код, использующий чистый WebNN API (без зависимости от полновесного ONNX Runtime). Важно точно понимать его возможности: инструмент работает **только с ONNX** (не с TensorFlow Lite) и поддерживает, в частности, конвертацию квантованных QDQ-моделей (Quantize-Dequantize).

```bash
python onnx2webnn.py \
  --input_onnx_file_path model.onnx \
  --output_js_path dist/model.js \
  --nhwc
```

Инструмент генерирует JavaScript-файл с функцией построения графа через вызовы WebNN API (`MLGraphBuilder`) и файл с весами модели, а также умеет учитывать предпочитаемый бэкендом порядок осей тензора (`preferredInputLayout` — NCHW или NHWC), который можно запросить через `context.opSupportLimits()`.

Этот подход в перспективе позволяет отказаться от тяжёлых библиотек (полновесный ONNX Runtime) и уменьшить размер бандла — но, как и всё остальное в этой главе, сегодня применим только в средах, где WebNN в принципе доступен.

### 2.4. Операторы, поддерживаемые WebNN

Спецификация WebNN определяет широкий набор операторов, покрывающих большинство современных нейросетевых архитектур. Между версией Candidate Recommendation Snapshot от 11 апреля 2024 года и обновлённой версией от 22 января 2026 года спецификация претерпела более 100 значимых изменений — в частности, добавилась третья волна операторов для более полной поддержки трансформеров (включая операции `dequantizeLinear`, `quantizeLinear` и attention-операции) и упомянутый выше MLTensor API.

**Категории операторов в спецификации 2026 года:**

- **Базовые:** `Add`, `Mul`, `Sub`, `Div`, `MatMul`, `Concat`, `Reshape`, `Transpose`, `Slice`, `Split`.
- **Активации:** `Relu`, `Sigmoid`, `Tanh`, `Gelu`, `HardSigmoid`, `LeakyRelu`.
- **Свертки:** `Conv`, `ConvTranspose`, `DepthwiseConv`, `AveragePool`, `MaxPool`.
- **Нормализация:** `BatchNormalization`, `LayerNormalization`, `InstanceNormalization`.
- **RNN/LSTM:** `LSTM`, `GRU` (с поддержкой сложных recurrent-архитектур).
- **Трансформеры:** `MultiHeadAttention`, `RotaryEmbedding`, `GroupQueryAttention`.
- **Квантование:** `QuantizeLinear`, `DequantizeLinear`.

Точное число поддерживаемых операторов ONNX/TFLite в каждой конкретной реализации браузера может отличаться от заявленного в спецификации — перед использованием конкретного оператора в продакшне стоит проверять его поддержку через feature detection, а не полагаться на общий список.

### 2.5. Dead Ops и редукция графа

Инструменты экосистемы WebNN (включая конвертеры вроде `onnx2webnn` и ONNX Runtime Web) применяют механизм, который в комьюнити принято называть **Dead Ops** (мёртвые операторы). Если модель содержит оператор, не поддерживаемый WebNN (например, `TopK` или `Range`), конвертер:

1. Отмечает выходы этого оператора как "мертвые" (dead).
2. Распространяет статус "dead" через все зависимые операции.
3. Экспортирует последние "живые" (live) выходы до зоны мертвых операторов, отбрасывая все, что находится за ней.

**Результат:** граф всегда успешно собирается, не поддерживаемые операторы просто исключаются из выполнения. Это полезный механизм толерантности к неполной поддержке операторов — но стоит понимать, что «граф собрался» не означает «модель работает корректно»: если отброшенный оператор был функционально важен, результат инференса может оказаться неполным или неверным, и это нужно проверять на реальных данных, а не полагаться на сам факт успешной сборки.

## 3. Сценарии использования WebNN в перспективе

Спецификация WebNN описывает десятки прикладных сценариев использования аппаратно-ускоренного инференса в браузере. Все они ниже описывают целевое, проектное состояние технологии — то, ради чего WebNN разрабатывается, — а не то, что уже массово работает у пользователей в 2026 году.

### 3.1. Ресайз изображений (Super Resolution)

При низком разрешении видеопотока из-за сетевой перегрузки WebNN в перспективе сможет запускать модель супер-разрешения (например, SRGAN) для повышения качества, выполняя такие модели на NPU в реальном времени с минимальным энергопотреблением.

```javascript
// Запуск super-resolution через ONNX Runtime Web
const session = await ort.InferenceSession.create('superres.onnx', {
    executionProviders: ['webnn']
});

const inputTensor = new ort.Tensor('float32', lowResImageData, [1, 3, 480, 640]);
const result = await session.run({ 'input': inputTensor });
const highResImage = result.output.data;
```

### 3.2. Удаление шума из аудио (Noise Suppression)

WebNN в перспективе должен позволить выполнять подавление шума в реальном времени (RNNoise, Whisper-based denoising) полностью на клиентской стороне.

Ключевое потенциальное преимущество: **все данные остаются на устройстве пользователя**. Это важно для конфиденциальных разговоров и соблюдения регуляторных требований (GDPR, HIPAA) — хотя строго говоря, регуляторное соответствие зависит от конкретной архитектуры приложения в целом, а не гарантируется самим фактом локального инференса:

- В аудио- и видеоконференциях для подавления фонового шума.
- В системах распознавания речи для очистки аудиопотока перед транскрипцией.
- В приложениях для людей с нарушениями слуха (чистая речь для слуховых аппаратов).

### 3.3. Перевод речи в реальном времени (Speech Recognition)

Один из самых впечатляющих целевых сценариев — выполнение моделей распознавания речи (например, Whisper) на NPU в реальном времени.

**Ориентир по производительности:** по данным, публикуемым производителями NPU (в частности, применительно к Snapdragon X Elite), инференс класса Whisper на выделенном NPU способен работать на порядок быстрее реального времени звучания аудио. Важно понимать источник таких цифр: это бенчмарки нативного NPU-инференса на конкретном чипе, а не измерения производительности именно через браузерный WebNN API, который на момент написания книги ещё не вышел за пределы экспериментальной поддержки — то есть воспроизвести такие цифры именно из браузера сегодня нельзя, только через нативные ML SDK производителя.

**Пример целевого воркфлоу** (архитектурная идея, к которой стремится экосистема):

```
VAD (AudioWorklet + WASM) → ASR (WebNN на NPU) → LLM (WebGPU)
→ TTS (WebNN на NPU) обратно
```

Весь пайплайн задуман для полностью локального выполнения, без отправки данных на сервер.

```javascript
// Распознавание речи через WebNN (целевой сценарий; на практике сегодня
// используйте transformers.js/ONNX Runtime Web с backend'ом WebGPU или WASM)
const session = await ort.InferenceSession.create('whisper-base.onnx', {
    executionProviders: ['webnn']
});

// Аудио с микрофона → спектрограмма → инференс → текст
const audioData = await getMicrophoneAudio();
const melSpectrogram = preprocessAudio(audioData);

const result = await session.run({ 'mel': melSpectrogram });
const transcript = postprocessText(result.output);
```

### 3.4. Другие сценарии, специфицированные W3C

Спецификация WebNN описывает следующие сценарии как целевые применения аппаратно-ускоренного инференса в браузере:

- **Обнаружение лиц (Face Detection).** В системах видеонаблюдения и конференц-связи.
- **Семантическая сегментация (Semantic Segmentation).** Удаление или размытие фона в онлайн-встречах для приватности.
- **Детекция скелета (Skeleton Detection).** Распознавание жестов и языка тела.
- **Распознавание лиц (Face Recognition).** Аутентификация и проверка присутствия.
- **Обнаружение эмоций (Emotion Analysis).** Анализ настроений в чатах и видео.
- **Машинный перевод (Machine Translation).** Мгновенный перевод текста в реальном времени.

Все перечисленные сценарии уже сегодня реализуемы на практике — но через связку WebGPU + transformers.js/ONNX Runtime Web, а не через WebNN.

## 4. Безопасность и приватность

Спецификация WebNN закладывает механизмы защиты от угроз, связанных с выполнением нейросетевых моделей:

- **Изоляция модели.** Модели должны выполняться в изолированной среде браузера, без доступа к файловой системе или другим сайтам.
- **Фингерпринтинг.** Спецификация WebNN включает средства защиты от создания цифровых отпечатков устройства через измерение производительности модели, в частности, **coarse-grained (грубое) возвращение временных значений**.
- **Локальное выполнение.** Модели выполняются на устройстве пользователя без отправки данных в облако. Это сохраняет приватность данных (аудио, видео, текст) и позволяет использовать ИИ в офлайн-режиме — но, опять же, этот принцип в 2026 году на практике реализуется через WebGPU-стек, а не через сам WebNN.

## Итог

WebNN (Web Neural Network API) — это перспективный стандарт, который должен превратить браузер в платформу для аппаратно-ускоренного выполнения нейросетевых моделей с доступом к CPU, GPU и NPU через унифицированный интерфейс. Спецификация достигла статуса Candidate Recommendation в январе 2026 года, что является реальным прогрессом.

Но по факту реализации в браузерах на 2026 год картина куда скромнее, чем предполагает название главы:

- **Поддержка браузеров.** Только Chrome, и только в рамках Origin Trial (примерно версии M147–M149). **Firefox и Safari WebNN не реализовали** — вопреки распространённому заблуждению, ONNX Runtime Web не может «добавить» поддержку WebNN в браузер, где отсутствует нативный `navigator.ml`.
- **Реалистичный прогноз.** По независимым оценкам, production-путь для WebNN — это 2027 год, а не 2026-й.
- **Рабочая альтернатива уже сегодня.** WebGPU в связке с transformers.js или ONNX Runtime Web (backend WebGPU/WASM) — это стек, который реально работает в продакшне 2026 года и обеспечивает большинство сценариев, описанных в этой главе (супер-резолюция, шумоподавление, распознавание речи), пусть и без прямого доступа к NPU.
- **MLTensor, onnx2webnn и остальная экосистема** — технически интересны и стоят изучения на перспективу, но применимы сегодня только в контролируемых средах с доступным Chrome Origin Trial, не в массовом продакшне.

В следующей главе мы рассмотрим WebAssembly 2.0 и Component Model — технологии, которые, в отличие от WebNN, уже сегодня позволяют выполнять нативный код в браузере с производительностью, близкой к "железу", и куда более зрелым статусом кросс-браузерной поддержки.
