# Глава 13. Защита от цифровых отпечатков (Fingerprinting)

Цифровой отпечаток (fingerprint) — это уникальный набор характеристик устройства и браузера, который позволяет идентифицировать пользователя без использования файлов cookie или других явных идентификаторов. В 2026 году борьба с фингерпринтингом стала одним из ключевых направлений развития браузерной платформы. Эта глава рассматривает три основных механизма защиты: сокращение и реструктуризацию User-Agent через клиентские подсказки, изоляцию хранилища (Storage Partitioning) и баланс между аналитикой и приватностью.

---

## 1. Новые заголовки клиентских подсказок (Client Hints)

### 1.1. Проблема User-Agent строки

Исторически User-Agent строка передавалась с каждым HTTP-запросом и содержала обширную информацию о браузере, операционной системе, версии и даже модели устройства . Это создавало две фундаментальные проблемы:

- **Чрезмерная детализация.** Гранулярность данных позволяла идентифицировать пользователей пассивно, без их ведома.
- **Отсутствие контроля.** Данные отправлялись по умолчанию, и сайт не мог отказаться от их получения, что давало возможность скрытого отслеживания .

### 1.2. UA-CH: User-Agent Client Hints

**User-Agent Client Hints (UA-CH)** — это механизм, который заменяет пассивную передачу детальной информации моделью активного запроса . Вместо того чтобы отправлять всю информацию в каждом запросе, браузер теперь отправляет только базовый набор "низкоэнтропийных" данных по умолчанию. Остальные данные передаются только когда сервер явно запрашивает их через заголовок `Accept-CH` .

**"Низкоэнтропийные" заголовки, отправляемые по умолчанию** :

| Заголовок | Пример | Описание |
|-----------|--------|----------|
| `Sec-CH-UA` | `"Chrome"; v="146"` | Бренд браузера и значимая версия |
| `Sec-CH-UA-Mobile` | `?1` | Признак мобильного устройства |
| `Sec-CH-UA-Platform` | `"Windows"` | Название платформы |

**"Высокоэнтропийные" заголовки, требующие явного запроса** :

| Заголовок | Пример | Описание |
|-----------|--------|----------|
| `Sec-CH-UA-Full-Version` | `"146.0.1.2"` | Полная версия браузера |
| `Sec-CH-UA-Platform-Version` | `"15.0"` | Версия ОС |
| `Sec-CH-UA-Arch` | `"ARM64"` | Архитектура процессора |
| `Sec-CH-UA-Model` | `"Pixel 9 Pro"` | Модель устройства |
| `Device-Memory` | `8` | Объем оперативной памяти (ГБ) |
| `Viewport-Width` | `1920` | Ширина области просмотра |

### 1.3. Механизм работы Client Hints

Процесс получения детальной информации о клиенте выглядит следующим образом :

1. **Браузер отправляет запрос** с базовыми заголовками (низкоэнтропийными).
2. **Сервер отвечает** с заголовком `Accept-CH`, перечисляя дополнительные Client Hints, которые он хотел бы получать :

```
HTTP/1.1 200 OK
Content-Type: text/html
Accept-CH: Sec-CH-UA-Model, Sec-CH-UA-Platform-Version, Device-Memory
```

3. **Браузер сохраняет** запрошенные предпочтения для текущего origin на длительность сессии.
4. **При последующих запросах** к этому origin браузер добавляет запрошенные заголовки:

```
Sec-CH-UA-Model: "MacBook Pro 16"
Sec-CH-UA-Platform-Version: "15.5"
Device-Memory: 16
```

**Critical-CH:** Если для корректной загрузки страницы требуются определенные Client Hints в первом же запросе, сервер может использовать заголовок `Critical-CH`. Это заставляет браузер перезапросить страницу с необходимыми заголовками, если они не были отправлены в первом запросе .

### 1.4. Требования безопасности

Client Hints работают только через защищенное соединение (HTTPS). Заголовки `Accept-CH` игнорируются при передаче по незащищенному каналу . Это предотвращает перехват и подмену политик Client Hints в незащищенных сетях.

**Политика Permissions-Policy:** Контроль над тем, какие Client Hints могут быть переданы, осуществляется через заголовок `Permissions-Policy` . Это позволяет ограничить передачу данных о клиенте сторонним iframe и встроенным ресурсам.

### 1.5. Проблемы при переходе на UA-CH

**Сайты, которые использовали парсинг User-Agent строки, должны быть обновлены.** Сокращенная UA-строка по-прежнему доступна через `navigator.userAgent`, но содержит только бренд, значимую версию и платформу . Код, который пытается получить модель устройства или полную версию, должен быть переписан с использованием UA-CH API.

## 2. Storage Partitioning: изоляция хранилища

**Storage Partitioning** (изоляция хранилища) — это принцип, при котором все формы хранения данных на стороне клиента (cookies, localStorage, IndexedDB, кеш, Service Worker кеш) изолируются не только по origin, но и по контексту загрузки .

### 2.1. Как работает Storage Partitioning

В классической модели хранение данных было привязано только к origin: `https://example.com` мог получить доступ к своим данным независимо от того, загружен ли он как основная страница или как iframe на другом сайте.

В модели Storage Partitioning добавляется дополнительный уровень изоляции: **данные разделяются по топ-уровневому (top-level) origin** .

**Пример:**

- Пользователь заходит на `site-a.com`. Страница загружает iframe с `tracker.com`.
- `tracker.com` пытается установить cookie. Этот cookie сохраняется **в отдельной партиции** для `tracker.com` в контексте `site-a.com`.
- Пользователь переходит на `site-b.com`. Эта страница тоже загружает iframe с `tracker.com`.
- `tracker.com` пытается считать свой cookie. Он получает **другой** cookie — сохраненный в партиции для `tracker.com` в контексте `site-b.com`.

Таким образом, `tracker.com` **не может** использовать один cookie для отслеживания пользователя между `site-a.com` и `site-b.com`.

### 2.2. Типы хранилищ, подпадающих под Storage Partitioning

- **Cookies.** Поддерживается через CHIPS (Cookies Having Independent Partitioned State).
- **localStorage и sessionStorage.** Разделены по top-level origin.
- **IndexedDB.** Разделена по top-level origin.
- **CacheStorage (Service Worker).** Разделена по top-level origin.
- **Shared Workers.** Разделены по top-level origin.

### 2.3. Доступ к неразделенному хранилищу через Storage Access API

В некоторых легитимных сценариях (например, виджет авторизации "Войти через Google") требуется доступ к неразделенному хранилищу. Для этого используется **Storage Access API**:

```javascript
// Запрос доступа к неразделенному хранилищу
if (document.hasStorageAccess) {
    const hasAccess = await document.hasStorageAccess();
    if (!hasAccess) {
        // Запрашиваем доступ у пользователя
        const granted = await document.requestStorageAccess();
        if (granted) {
            // Теперь можно получить доступ к non-partitioned cookies
            // для текущего top-level контекста
        }
    }
}
```

### 2.4. Влияние на веб-экосистему

Storage Partitioning существенно ограничивает кросс-сайтовое отслеживание. Сторонние скрипты (аналитика, рекламные сети, виджеты) больше не могут использовать общие cookies или localStorage для идентификации одного и того же пользователя на разных сайтах. Это делает традиционную модель веб-аналитики, основанную на сторонних cookies, неработоспособной.

## 3. Баланс между аналитикой и приватностью пользователя

Сокращение User-Agent, изоляция хранилища и другие меры по борьбе с фингерпринтингом создают вызов для легитимных аналитических систем. В 2026 году существует несколько подходов к сохранению аналитики при соблюдении приватности.

### 3.1. Отказ от идентификации пользователя

Современная аналитика все чаще переходит от модели "индивидуальный пользователь" к моделям "поведенческие паттерны" и "сессии без связывания" . Вместо того чтобы отслеживать конкретного пользователя по всем сайтам, аналитика сосредотачивается на:

- Агрегированных данных о поведении на сайте.
- Сессионных событиях, которые не сохраняют идентификатор между визитами.
- Конверсиях, измеряемых без привязки к глобальному идентификатору.

**Federated Learning (Федеративное обучение):** В 2026 году набирает популярность подход, при котором модели машинного обучения обучаются локально на устройстве пользователя, а на сервер передаются только обобщенные параметры модели (градиенты), а не сырые данные . Это позволяет получать аналитические инсайты без сбора персональных данных.

### 3.2. Преимущества нового подхода для бизнеса

Несмотря на ограничения, новые подходы дают преимущества:

- **Снижение юридических рисков.** Отказ от сбора персональных данных через третьи стороны устраняет регуляторные риски (GDPR, CCPA).
- **Улучшение пользовательского опыта.** Отказ от баннеров согласия на cookies повышает доверие пользователей и улучшает конверсию.
- **Устойчивость.** Аналитические системы, не зависящие от третьих сторон и cookies, не ломаются при изменении браузерной политики.

### 3.3. Самостоятельный хостинг аналитики

Все больше компаний переходят на самохостинг аналитических платформ вместо использования облачных SaaS-решений (Google Analytics, Adobe Analytics) . Самохостинг дает полный контроль над данными, позволяет избежать передачи данных третьим сторонам и соответствовать требованиям локальных регуляторов.

## Итог

Борьба с фингерпринтингом в 2026 году ведется по трем ключевым направлениям:

- **User-Agent Client Hints (UA-CH).** Замена пассивной отправки детальной User-Agent строки на активную модель запроса через заголовок `Accept-CH`. По умолчанию отправляются только низкоэнтропийные данные; все остальные — только при явном запросе сервера.
- **Storage Partitioning.** Изоляция всех форм клиентского хранилища (cookies, localStorage, IndexedDB) по top-level origin. Сторонние ресурсы не могут использовать общее хранилище для отслеживания пользователя между разными сайтами.
- **Новая парадигма аналитики.** Переход от модели "индивидуальный пользователь" к поведенческим паттернам и сессионной аналитике. Использование федеративного обучения и самохостинга для получения инсайтов без нарушения приватности.
